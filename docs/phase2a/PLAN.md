## 实现前差距

- 原 E09 只有未来扩展讨论，没有真实需求贯穿变更。选取同一证据关联的“修订类型与填写解释”，保留 ID、端点与旧数据。
- 原 E10 已有新容器运行/重建和 CI，但缺少旧应用与新模式兼容、应用回滚及再次前滚的闭环。
- 原 E08 的 SQL 对照来自形似应用的合成表；需要对真实调查查询与真实 EF SQL 观察，不把独立表结果当作应用优化。
- Workspace 混合协议、Query 缓存、草稿、证据展示和结论表单。代码审查发现：保存过程中继续编辑可能被成功回调清除；后台刷新可能把 dirty 草稿的预期版本悄悄换成新版本；旧回执可能倒退缓存。先重现，再修复。
- 模板比较尚是摘要，需要按上游固定提交的 DI、behaviour、DbContext、事件时机和身份代码逐项比较，解释采用、简化、未采用及影响。

## 五个场景与门禁

| 场景 | 实施 | 完成证据 |
|---|---|---|
| A 真实需求变更 | 同一关联可在 Active 状态修订类型和解释；不增加模块 | 领域/API/DB/React、旧记录保留、端到端修订、发布说明 |
| B 数据演进 | 添加可空解释/修订时间；保留旧回执可反序列化；真实 EF 跟踪/SQL/事务观察 | 迁移前后数据、SQL 与版本条件、失败原子性、真实查询计划 |
| C 可靠 API | 原键确认已提交但响应丢失、旧版本、键误用、跨资源/账户拒绝 | API 与浏览器直接核对持久状态与审计，非伪造成功 |
| D 前端状态 | 分离服务端快照/已确认快照/草稿基线；响应时保留后来编辑；显式冲突确认；单调缓存 | 基线失败重现和修复后有因果断言的 Playwright |
| E 应用交付 | 从旧源构建、迁移、部署新应用、真实停库诊断、旧应用回滚保留新字段、再次前滚 | 本地 OCI 实际执行和相关 CI；Azure 仅设计 |

每场景按需求→影响→ADR→实现→测试→实验→证据→说明→验收推进。没有通过运行就不标 VERIFIED。`evidence/phase2a/` 与原 E01–E26 不混写。最终工程报告分别给出原 README、Phase 2A、教材编辑、云/生产限制四类结论。
