# 第 13 章 React Flow 与证据图谱的语义 {#ch13}

## 图谱首先是业务模型的投影

节点表示已调查证据，边表示由调查员建立的相互印证或矛盾关系。未调查正文不通过图谱泄漏；尚未发现的证据不被绘制成可连接节点。React Flow 提供视口、节点拖动、端点和边的交互，但不负责判断一条关系是否具有业务合法性。

建立关联可通过拖动端点，也可通过选择起点、终点和类型后点击按钮。两种交互调用相同 API，用相同版本和幂等策略提交。键盘替代路径同时提升可访问性和自动化稳定性；E2E 不必依赖像素拖拽来覆盖业务正确性。

## 本地节点位置与服务端关系分开

节点位置是呈现偏好，关联是业务事实。拖动一个节点不增加调查版本，也不会与另一窗口保存笔记发生冲突；建立或删除关联会推进根版本，并影响进入复核的门槛。这种划分让用户操作成本与业务含义一致。

React Flow 的受控节点使用 applyNodeChanges 更新组件状态。服务器快照变化后，已有节点保留原位置，新节点获得默认位置。离开视图后布局可以重建，界面对此有明确说明。若未来需要跨设备共享布局，应另建偏好模型或布局版本，避免把个人拖动当成调查证据变化。

## 无向边不能被控件字段误导

React Flow 连接数据使用 source 与 target，但领域关系是无向的。后端规范化两端顺序，去重 A–B 与 B–A；前端使用没有箭头的连线。颜色和标签共同表达关系类型，不只依赖颜色。否则色觉差异或黑白打印会失去含义。

删除关联通过边选择或文本关联列表完成。文本列表提供精确、可访问的删除按钮，不要求用户准确点击细线。删除也需要版本条件，提交后只读状态不能继续操作。一个“图形编辑器”仍然必须遵守整个调查状态机。

## 交互限制与服务端规则的重复

前端禁止自连，选择列表只包含已调查证据，非 Active 状态禁用连接。服务端仍重复检查这些规则，因为浏览器可被绕过，也可能在另一个窗口转换状态。对重复关联，前端没有用本地检查替代服务器唯一约束；服务器拒绝后显示明确错误并刷新。

图谱是可解释性工具，不是自动推理引擎。一条“相互印证”边代表用户的分析，不意味着服务器证明了两个陈述逻辑等价。评分只看固定案件规则与支持证据，不把图中边数当作现实推理可信度。

## 性能从规模假设开始

当前六个节点不需要虚拟化或复杂图布局服务。过早引入图数据库或分布式布局，会增加理解成本而没有可测收益。若节点增到数百，先测重渲染次数、拖动帧率、边路径计算和可见范围，再考虑 memo 化节点、分层展开与后台布局。

React Flow 包在前端主资源中占有明显体积，当前生产构建仍是一个主 JS 块。可以在后续把图谱视图懒加载，再对冷启动和切换耗时做对照。这个优化没有执行，因此本书不声称已经获得首屏性能改善。

## 实验 E13：同一关联能否被两种交互一致表达

先通过选择框建立门禁与凭证册的关联，确认图与文本列表都出现。刷新页面，关系仍存在；尝试反向重复建立，预期领域拒绝。删除后使用新的请求重新建立，确认版本与关联门槛变化。图谱截图来自真实页面，不是设计稿。

已有浏览器工作流验证了建立关联、图展示和最终提交；删除、自连和重复规则主要由领域与数据库测试覆盖。拖拽端点的精细手势、屏幕阅读器操作和大图性能没有独立实测，不能用已有选择框测试替代它们。

## 练习与参考答案

**13-A：** 为什么“保存布局”不应使用当前调查 Version？参考答案：布局不影响证据与结论语义。共用版本会产生无意义冲突；但若布局本身承载业务含义，如时间线排序，就必须重新分类并定义一致性规则。

**13-B：** 添加“因果关系”类型需要改变什么？参考答案：首先明确方向性，修改领域去重键和规范化逻辑，再更新数据库约束、API 合同、图箭头与测试。不能只增加一种颜色。

**13-C：** 设计一组图谱可访问性验收。参考答案：键盘选择两端、读取关系类型、建立与删除、明确焦点位置、无颜色依赖、错误提示可被辅助技术感知。当前只覆盖了其中部分能力。
