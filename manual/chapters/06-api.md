# 第 6 章 REST 合同、条件写入与错误恢复 {#ch06}

## 资源模型与动作语义

案件是可浏览定义，调查是某个用户拥有的持续资源。发现证据、进入复核和提交结论都是受业务约束的动作，不能简化成允许客户端任意 PATCH 状态字段。EchoCase 使用明确的动作端点，使服务端保留状态转换权；资源 ID 不携带所有权证明。

| 方法与路径 | 含义 | 写入条件 |
|---|---|---|
| GET /api/cases | 案件摘要 | 已登录 |
| POST /api/investigations | 开始调查 | CSRF、幂等键 |
| GET /api/investigations/{id} | 获取个人调查 | 资源所有权 |
| POST …/evidence/{id}/examine | 调查证据 | 版本、幂等、领域规则 |
| POST …/links | 建立无向关联 | 两端发现、规范化去重 |
| PUT …/notes | 替换笔记内容 | 版本、防丢更新 |
| POST …/state/review | 进入复核 | 发现与关联门槛 |
| POST …/verdict | 提交封存 | 复核状态、支持证据 |

端点没有在路径中加入 v1，因为当前只有一个受控客户端，尚无并行支持多个公共 API 版本的需求。OpenAPI 文档名称 v1 是文档标识，不代表已经建立了完整的版本生命周期策略。若出现外部消费者，应定义兼容规则、弃用时间和契约测试，而不是只加一个 URL 前缀。

## ETag 与 If-Match 是对用户意图的保护

GET 返回 ETag，例如 `"4"`。客户端保存时发送 If-Match: `"4"`，表明这次操作基于版本 4 的认识。服务器如果已经是版本 5，就不应悄悄覆盖。412 的意义不是“系统坏了”，而是“你依据的状态已过期，需要重新确认”。

当前实现只接受带双引号的正整数强版本标记，不接受星号、弱 ETag 或多个候选版本。这是有意收窄的应用合同，不能描述为完整实现 HTTP 条件请求规范。没有 If-Match 时返回 428，让遗漏保护的客户端尽早失败。

```http
PUT /api/investigations/{id}/notes
Cookie: echocase.session=...
X-CSRF-TOKEN: ...
Idempotency-Key: 01937cd1-e567-4fbe-a964-a8b9b84e2a93
If-Match: "4"
Content-Type: application/json

{"notes":"门禁与凭证记录需要交叉核对。"}
```

示例中的凭证省略，UUID 只是格式示意，不是运行证据。实际请求头由客户端根据当前快照和一次用户意图生成。

## 状态码需要稳定的机器语义

| 状态 | 机器代码示例 | 客户端应做什么 |
|---|---|---|
| 400 | csrf_invalid / invalid_request | 刷新防伪上下文或修正合同 |
| 401 | login_failed 或未登录 | 恢复身份，不重复业务动作 |
| 404 | investigation_not_found | 不继续尝试访问该资源 |
| 409 | key_reused | 这是不同请求，不能复用原键 |
| 412 | version_conflict | 刷新快照，保留草稿，让用户确认 |
| 422 | evidence_locked / invalid_transition | 解释业务规则，不自动重试 |
| 428 | precondition_required | 修复客户端缺少版本头的问题 |
| 503 | database_unavailable | 等待恢复，以原键确认不确定写入 |

问题详情供人理解，机器代码供程序分支。不要让前端用中文错误句子的子串决定恢复动作；文案改动不应改变正确性。追踪编号用于关联日志，也不应被当成用户身份或授权凭据。

## 生成类型解决什么，没解决什么

后端 OpenAPI 生成前端 schema.d.ts，客户端从 components 中引用 SessionView 等类型。它能在字段名称或数字类型变化时触发 TypeScript 编译问题。真实执行曾发现版本号被生成为 number | string；原因是 JSON 数字读取策略较宽松。后端改为严格数字后再生成，合同收敛到 number。

生成类型不能在运行时证明远端 JSON 正确，也不会自动添加 CSRF、If-Match 或幂等头。本项目的显式客户端承担这些协议行为。若引入不可信外部 API，可以再增加运行时 schema 校验；当前通过 API 合同负测试和 E2E 共同验证同仓库两端。

## 实验 E06：让合同漂移变成可见失败

发送 Notes 为 null 的请求，预期 400；发送额外 OwnerId，预期 400；用非法版本头请求，预期 428。然后从真实 API 再生成 schema.d.ts，与提交文件比较。若差异存在，CI 应失败，提醒同时提交客户端合同更新。

这个门禁需要格式稳定。生成文件不应再被自动格式化器改写，否则仅空格差异也会让合同检测失败。本项目把生成文件加入格式化忽略列表，并将契约再生成作为交付检查的一部分。

## 练习与参考答案

**6-A：** 412 与 409 是否可以互换？参考答案：当前合同把条件版本不满足表达为 412，把同幂等键指向不同请求表达为 409。两者恢复方式不同，混用会让客户端无法判断需要刷新状态还是修正键管理。

**6-B：** 返回原幂等回执后，是否可以直接把它当成最新调查？参考答案：不能。它证明原操作效果，不保证没有后续更新。客户端接收后还会使查询失效，重新获取当前快照；响应版本也可以防止盲目覆盖更晚缓存。

**6-C：** 给未来“下载调查报告”设计缓存规则。参考答案：先明确它是某个封存版本的不可变报告还是实时个人视图；个人实时 API 使用 no-store，静态且经过授权的版本化导出可以采用不同缓存策略。不能沿用公共静态资源的缓存配置。
