# 第 6 章 HTTP 合同中的版本、意图与失败

HTTP 把一次业务交互变成跨进程协议。客户端看到的是请求、响应和超时，不会自动知道事务是否提交。一个可靠的写接口因此需要表达三件事：操作哪个资源，基于哪个已知事实，以及这是否为同一次尝试。EchoCase 用资源路径、If-Match 和 Idempotency-Key 分别承载它们。

## 6.1 URI 与方法表达什么

调查是主资源，证据调查和关系修订围绕它组织。读取单个调查返回 SessionView，成功写入同样返回完整视图及 ETag。PUT 到已有 linkId 修改关系类型和解释，不替换端点；DELETE 删除关系；POST 表达建立调查、调查证据和状态动作。选择方法不能单独决定重试安全，实际业务协议仍要说明命令是否可能重复产生新版本。

EchoCase 不把整个实体暴露成一个通用 PATCH。客户端不能直接写 Version、OwnerId、Score 或 Status。进入复核、返回调查和提交结论有不同前置条件，因此需要语义明确的用例。这样的接口使“允许哪些变化”可从路径与请求类型读出，也减少了批量属性赋值绕过规则的机会。

## 6.2 If-Match 是决定的前提

{{code api-version}}

Version 要求一个带双引号的正整数。当前实现接受单个强样式版本标签，不支持弱标签、标签列表或星号。解析失败使用 428 表达缺少可接受前提。ETag 在成功响应中采用同样形式，因此客户端可以把已确认版本带回写请求。

这个版本是调查聚合的应用版本，不是数据库 xmin，不是修改时间，也不是 JSON 字节哈希。服务端先比较客户端前提与已加载版本，EF 保存时还会把跟踪原值放入 UPDATE 条件。前一次比较提供及时反馈，后一次比较关闭真实竞争窗口，两者缺一都不能完整说明并发行为。

```http
If-Match: "4"
Idempotency-Key: <本次意图的 UUID>
```

上面是协议形状说明，尖括号不是实际发送值。如果用户基于版本 4 修订关系，而另一个窗口已提交版本 5，服务器拒绝此次新意图。它不能自动把请求“升级”为基于 5 的判断，因为用户从未见过版本 5 中的事实。

## 6.3 幂等键识别的是一次意图

{{figure intent-coordinates}}

相同内容的两次点击未必是同一次意图。用户第一次保存后再次确认相同内容，系统可能把它当作另一次命令；网络重试则应保留原键。当前 SaveNotes 并非天然 no-op：正常成功会推进版本。因此，即使方法使用 PUT，客户端仍需使用应用幂等协议，才能在响应丢失时确认第一次提交而不额外执行。

同一 owner/key 的回执已存在且指纹相同，服务器返回历史结果。指纹不同则 409，表示客户端把一个键拿去表达另一项请求。若原键不存在但资源版本过期，则 412。409 关心意图身份，412 关心资源前提，二者不应被压成同一个“保存失败”。

## 6.4 错误分类应帮助下一步决定

{{figure http-outcomes}}

400 表示请求形状或防伪令牌等问题，401 要求认证，404 统一资源不存在与不可见。422 说明请求进入业务后违反了规则；412 要求用户核对资源变化；409 要求修复幂等键使用。429 是请求频率约束，503 表示暂不可用的服务条件。客户端展示应保留有助判断的 code、detail 和 traceId，而不是根据所有非 200 结果统一清空表单。

“结果未知”却不是服务器返回的某一个状态码。fetch 失败时客户端没有完整响应，成功正文无法解析时也没有可使用的结果。当前客户端把这些情况包装为 status 0，以阻止继续发出不同写入，并允许原样重试。这是浏览器本地的分类，不是合法 HTTP 状态码，更不能在 API 文档里写成服务器会返回 HTTP 0。

## 6.5 读合同也需要边界

单个调查的查询同时筛选 Id 与 OwnerId，完整视图反映一个查询语句的快照。API 对 /api 设置 no-store，避免普通 HTTP 缓存把私人数据当成可共享资源。浏览器内 TanStack Query 仍可以管理应用层缓存，因为那是有身份和生命周期的 JavaScript 状态，不等同于共享代理缓存。

列表最多取五十个调查，按 UpdatedAt 倒序。它没有游标，也没有在相同时间戳时显式增加 Id 的稳定分页次序。当前界面因此是有限总览，而不是可遍历任意历史数据的完整分页合同。如果未来要求审阅全部旧档案，需要新增明确的分页语义，不能仅把 Take 的数字调大。

Get 与 List 使用 AsNoTracking，避免为了展示而维护写入快照。Graph 选择单语句加载，使根、发现和关系共享同一语句快照。一次读取仍可能在返回浏览器前就被新写入超越，所以界面显示的“当前版本”应理解为当前已确认快照，而不是所有客户端共同认可的绝对现在。

## 6.6 OpenAPI 与 TypeScript 提供怎样的保证

schema.d.ts 从 API 合同生成，前端通过 components 的 schema 类型引用 Session 和 ReviseLinkRequest，减少手写字段漂移。它能在构建时发现字段名或可空类型不匹配，却不会在运行时验证 response.json 的每个值。泛型 request<T> 是类型承诺，不是 JSON schema 校验器。

同样，自动文档不能完整表达 Idempotency-Key 的持久回执语义，也不能替代对 If-Match 接受子集的说明。机器可读合同处理形状，人类可读合同解释时间和决定。二者配合，才能让一个客户端在失败后知道该保留原意图、重新认证，还是请求用户重新确认。

## 6.7 条件写入与条件读取不要混为一谈

响应带 ETag，不代表应用已经实现 If-None-Match 和 304 条件读取。当前代码在写端解析 If-Match，在成功响应中返回版本，并对 API 设置 no-store。它主要把标签作为写入前提，不是一套完整 HTTP 缓存协商实现。

同样，这份解析器是项目公开接受的有限形式，不是完整实体标签语法库。维护者若打算支持列表、星号或弱标签，需要先定义它们如何对应单个聚合版本，再调整解析和验证。不能只让字符串“能被 int.Parse”就假装支持全部标准条件头。

版本还不能跨资源比较。调查 X 的 8 与调查 Y 的 4 没有谁更新的全局含义；键和缓存必须同时包含资源身份。时间戳也不能替代这种身份范围，尤其当同一时刻创建多个独立调查时。

## 6.8 状态码之后还需要可理解的正文

412 告诉客户端前提失败，却没有自动完成用户的比较决定。界面仍需取得当前调查，保留本地草稿并解释基线差异。422 告诉客户端业务拒绝，却不能仅显示数字；稳定 code 适合程序分类，面向人的 detail 解释如何调整。

TraceId 的作用是定位本次请求，不是业务错误类别，也不是授权令牌。用户可以复制它帮助排查，但它不能替代明确 code，更不能据此访问另一个用户的资源。将诊断编号、错误语义和业务身份分别建模，接口才不会成为一团“字符串约定”。

HTTP 层的教学重点因此不止是方法和路径。它把用户决定的条件、服务器的可公开结论以及客户端下一步行动接起来。协议越明确，前端越少需要猜测，失败恢复也越容易保留正确意图。
