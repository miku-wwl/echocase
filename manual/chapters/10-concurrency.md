# 第 10 章 根版本与事务如何共同拒绝过期写入

在页面上禁用保存按钮，只能阻止这个页面再次点击。另一个标签页、另一个请求或同一用户的另一台设备仍可能修改调查。真正的仲裁必须发生在持久层，而且必须保护根与子对象形成的完整决定。

## 10.1 两次版本检查关闭两个不同窗口

Store 加载调查后，先比较 aggregate.Version 与 ExpectedVersion。若用户发来版本 4，而当前已是 5，就立即返回 412。这个检查给常见过期窗口提供清晰反馈，却不是最终并发保证：比较完成后，到 SQL 保存之前，另一个事务仍可能提交。

因此模型又把 Version 标为 concurrency token。EF 保存使用加载时原值作为 UPDATE 条件；若另一事务已推进根版本，旧条件不再匹配。前面的 if 是应用层快速判断，后面的 WHERE 是数据库中的原子条件。只保留前者会有检查与使用之间的空隙，只保留后者则把容易识别的旧请求也拖到保存阶段。

## 10.2 真正同时读到旧版本时会发生什么

{{figure cas-race}}

真实 Store 竞争使用两个独立 DbContext、两个不同幂等键，让双方在领域回调的屏障前都完成加载。这个同步条件很重要：若只是依次发两个请求，后者可能在读取时就看到新版本，只验证了前置 if，没有触及数据库竞争。

两方实际隔离均为 ReadCommitted，最终结果是一个 200、一个 412，根停在版本 5；成功修订的审计和回执各保留一条。这些观察合在一起，说明仲裁不仅返回了不同状态，还保护了持久结果。不同幂等键没有让操作互相重放，它们确实在竞争同一个根。

对于根 UPDATE 的条件写路径，后来的写者可能先等待前一个写者。前者提交后，条件会针对可更新的行重新判断；旧 Version 不再匹配时，更新不能假装仍然成功。EF 根据应更新但未更新的结果抛出并发异常。[EF 并发令牌](https://learn.microsoft.com/en-us/ef/core/saving/concurrency)

## 10.3 子实体没有版本列，为什么仍能保护

{{figure transaction-set}}

关联修订改变 Links 行，根只改变 UpdatedAt 和 Version。两条修改必须在同一个事务。只要根条件失败，子修改就不能单独留下；如果先把子表提交，再尝试推进根版本，就会出现“接口返回冲突，但关系已被改写”的破坏性结果。

当前领域保证每项成功修改推进根一次，Store 把根、子、审计和回执放入同一次 SaveChanges 和同一显式事务。这是可推理的协议：一次用户决定对应一个新根版本，所有附属事实共享成败。数据库没有魔法识别 DDD 聚合，保证来自这条具体写入路径。

## 10.4 为什么还捕获一个唯一约束异常

{{code store-conflicts}}

实际批次里，Audit 的 INSERT 可能排在根 UPDATE 前面。Audit 对 (InvestigationId, Version) 有唯一索引；两个基于版本 4 的决定都会尝试插入版本 5 的审计。后来的事务可能先在该唯一键上等待并失败，尚未到达根 UPDATE。

因此 Store 只对指定约束 `IX_Audit_InvestigationId_Version` 的 PostgreSQL 23505 映射为 412。不能把全部唯一约束失败都叫版本冲突：关系对重复、邮箱重复或回执键错误都有不同语义。精确匹配约束名，是避免误分类的关键。

```sql
INSERT INTO "Audit" (..., "Version") VALUES (..., @p4);
UPDATE "Investigations" SET "UpdatedAt" = @p5, "Version" = @p6
WHERE "Id" = @p7 AND "Version" = @p8;
```

这是实际批次顺序的压缩展示，省略号仅省去审计其他列，不能作为可执行 SQL。它提醒读者：代码中先改变根属性，并不决定 EF 批次一定先发送根 UPDATE。要解释异常来源，必须知道真正执行的语句与约束。

## 10.5 回滚后的对象与数据库不是同一个状态

事务失败后，当前内存对象可能仍带着尝试过的新属性值。数据库回滚不会把每个 CLR 对象自动恢复成旧值。EchoCase 抛出错误并结束本请求作用域，不把这套对象当作成功资源返回，也不继续在同一上下文中处理下一项业务。

客户端同样不应该用失败请求正文替换确认缓存。用户的草稿可以保留，因为它是尚未成立的意图；服务器确认状态则需要读取实际持久事实。把这两类状态混在一个对象中，往往导致“回滚”时误删新输入，或把失败值显示成已保存。前后端在这里必须共享相同的成败语义。

## 10.6 冲突处理为什么不能自动覆盖

假设 A 修改笔记，B 修订关系，两者都基于版本 4。保守的根版本策略会拒绝一个决定，即使它们改动不同字段。是否可以自动合并，需要业务判断：B 的解释可能依赖 A 刚纠正的笔记事实，单纯“字段不重叠”并不足以证明独立。

当前应用要求用户看到变化后重新确认。若未来要支持字段级版本或自动合并，应明确哪些决定能够交换顺序、如何检测语义相关性，以及审计版本如何解释。更高并发不是免费改进，它会改变用户承诺与推理复杂度。

这里的乐观来自用户编辑期间不持有数据库锁，而不是完全没有锁。真正保存时数据库仍需要行和索引层面的同步。同样，它也不意味着冲突可以忽略。合理的界面应保留意图、展示当前事实，并让用户作出新的决定。

## 10.7 审计唯一键为什么不能取代根条件

版本审计唯一键会阻止两个事务同时记录同一调查版本，但它保护的是审计事实。若某条写路径不写审计，或错误地产生不同版本号，它就不再覆盖竞争。根 UPDATE 的 WHERE 则直接把修改与读取原值联系起来，属于资源本身的保护。

保留两者不是重复设计同一个锁。根条件表达“我基于这个版本修改”；审计唯一性表达“一个调查版本只对应一个操作记录”。它们碰巧能在部分竞争中较早发现同一冲突，错误分类才需要识别不同数据库表面的失败来源。业务含义仍各自清楚。

如果未来一次操作对根推进两次，审计只记录最终版本，唯一索引也不会自动发现中间版本被跳过。因此“每个成功行为只推进一次”仍是领域与用例的合同，需要有针对性验证。数据库保证和程序保证的组合才构成完整模型。

## 10.8 从失败结果反推验证强度

两个请求返回 200/412，还可能只是后者很晚才读到新版本。只有确认双方都加载旧版，才能说明数据库竞争路径被触及；只有检查子关系、回执和审计，才能说明失败没有部分落库。每增加一个观察，排除的错误解释就更具体。

反过来，一次竞争测试不能证明所有调度顺序都已穷尽。它验证的是被同步条件明确构造的关键窗口，源代码和数据库机制帮助将结论推广到同类情况。工程论证由模型与观察共同组成，任何一边单独都不够。
