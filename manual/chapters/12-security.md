# 第 12 章 可信身份、资源所有权与浏览器安全

调查是私人资源。保护它不仅要知道“用户是否登录”，还要知道“这个用户是否能访问这一份调查”，以及“这个浏览器写请求是否来自可信交互”。认证、授权、防伪和内容投影对应不同边界，任何一个都不能凭另一个存在而省略。

## 12.1 Identity 与 Cookie 分别做什么

Identity 的 UserManager 负责账户存储、密码检查和失败次数。登录成功后，应用构造包含 NameIdentifier 与 Name 的 ClaimsPrincipal，再通过指定 Cookie scheme 签入。后续请求由 Cookie 认证恢复身份，而不是重新把邮箱和密码放进每个业务正文。

Cookie 使用 HttpOnly 与 SameSite Strict；非开发、非测试环境要求 Secure。会话有效期两小时，不滑动延期。API 未登录时返回 401，避免把 JSON 客户端重定向到一个 HTML 登录页。浏览器可读的邮箱用于展示，资源访问使用稳定用户 Id。

这些配置并不等同完整企业账户生命周期。当前手工 Cookie principal 没有完整实现安全戳持续验证、全设备撤销、多因素认证、确认邮箱和密码重置流程。Identity 提供相关能力，不代表只引用它就自动接上所有能力。评审应读实际注册和验证路径，区分已用机制与框架潜力。

## 12.2 Owner 必须来自可信上下文

业务请求不接收 OwnerId。端点从已认证 claims 取得 owner，再向下传递。Store 在 SQL 中同时筛选调查 Id 与 OwnerId，未知或不可见统一为 404。它既避免把其他用户的数据读进内存后再判断，也减少通过响应差异探测某个 Id 是否存在的机会。

{{figure security-boundaries}}

资源过滤要覆盖 Get、List 和 Write，不能只在页面加载时检查一次。即使客户端隐藏了某条按钮，用户仍能直接发请求；即使 Guid 难以猜测，也不构成授权。幂等回执路径同样先验证资源，避免重放绕开所有权。

没有团队或管理员角色是当前业务范围的决定。将来新增共享调查，需要定义成员、权限变化和回执可见性。不能仅删除 owner 过滤，就把私人应用改造成安全协作系统。

## 12.3 Cookie 会自动发送，所以需要防伪

浏览器会根据站点和 Cookie 规则自动携带会话凭证。服务端看到有效 Cookie，只能确认浏览器拥有会话，不能单凭它证明这次写入是用户在本应用中作出的决定。CSRF 令牌把浏览器可取得的请求令牌与对应 Cookie 联系起来，写 API 要求 X-CSRF-TOKEN。[ASP.NET Core 防伪](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0)

客户端先从 /api/auth/csrf 获取令牌，再在写请求中发送。登录、注册也经过防伪中间件。登出后客户端重新取得令牌，避免身份切换后沿用旧交互上下文。SameSite Strict 减少跨站发送，但不能代替明确的服务器防伪规则。

CSRF 与 XSS 不同。若攻击者已能在本应用同源脚本中执行任意代码，往往可以读取请求令牌并发起同源请求。HttpOnly 限制脚本直接读取会话 Cookie，不能阻止恶意同源脚本利用现有会话。因此还需要内容输出和脚本来源边界。

## 12.4 不发送的内容，比隐藏的内容更可靠

{{figure ui-evidence}}

SessionPresenter 只有在证据已调查后才发送 Body。锁定证据的摘要也被替换为统一提示。这个边界成立在服务器投影中，浏览器无需先获得全部秘密再用 CSS 隐藏。界面的锁图标只是解释当前状态，不能独自承担内容保护。

React 默认把普通文本作为文本节点输出，当前笔记与解释没有作为任意 HTML 注入。若未来允许富文本，需要重新定义可接受标记、清理与渲染过程；把字符串类型改成 HTML 并不会自动继承现有安全性。

API 的 no-store 限制 HTTP 缓存行为。Query 缓存则按 owner 与 id 分区，登录和登出时清除非 me 查询，避免同一浏览器切换账户后看到上一人的数据。服务端授权仍然是最终保证，客户端清缓存保护的是界面隔离和合理体验。

## 12.5 安全头与频率约束的实际含义

CSP 主要限制脚本、连接、图片等来源，并禁止被其他页面作为 frame 嵌入。当前 style-src 允许 unsafe-inline，以兼容实际样式和图谱内联呈现，不能把这份策略形容成完全禁止内联内容。nosniff 与 no-referrer 降低类型猜测和外链信息暴露。

认证端点按远端 IP 固定窗口限流，每分钟十五次；业务写入按用户 Id，每分钟一百二十次。固定窗口在边界附近可能允许短时突发，不是平滑流量保证；进程内限流器也不自动形成多实例全局配额。若入口经过代理，可信转发地址配置会影响 IP 身份，当前代码没有因此获得任意部署下准确客户端地址的保证。

密码失败锁定与限流针对不同成本。前者记录账户失败，后者限制请求速度。错误正文应避免不必要的账户存在性泄露，内部定位则通过 TraceId 关联。把这些行为连成威胁与边界的解释，比罗列“使用了 Cookie、CSP、Identity”更能评估实际保护。

## 12.6 安全评审回到业务事实

一条修订请求要同时满足：有可信身份，目标属于该身份，写入来自有效防伪上下文，请求形状可接受，领域允许，版本没有过期，意图没有被改写。每一层拒绝的理由不同，客户端的下一步也不同。

安全不是独立放在工程末尾的一页配置。它决定了 owner 如何进入所有层、哪些数据允许进入读模型、缓存如何分区，以及重试能否越过资源边界。后面的 React 设计会继续使用这些事实，而不是把浏览器当作天然可信环境。

## 12.7 同源开发与文档安全策略

生产静态界面由 API 宿主提供时，页面响应上的 CSP 才约束该页面后续脚本和连接。开发时前端由 Vite 提供，API 的 JSON 响应上带 CSP，并不会自动成为 Vite 页面自己的文档策略。检查某个 API 头存在，不能直接证明所有开发页面执行相同安全边界。

前端 request 使用相对路径与 same-origin 凭证，通过既定开发代理或同源宿主访问 API。浏览器的同源、SameSite 和服务端的身份判断分别有不同范围。它们协作构成会话路径，不能用“后端有 CORS”一类泛泛说法代替真实部署和请求来源分析。

对教材而言，关键是能把每项配置连接到它实际保护的对象：HttpOnly 保护 Cookie 的脚本可读性，CSP 约束文档执行，CSRF 保护写请求意图来源，owner 过滤保护资源可见性。保护对象明确，配置才不只是术语清单。

## 12.8 失败处理也有信息边界

404 合并不可见与不存在，有助于减少资源探测信息；登录失败用统一文字，不把“用户不存在”与“密码错误”直接展示成两个业务提示。它们不会消除所有时序差异，也不构成完整抗枚举证明，但体现了公开合同对内部事实的选择。

数据库异常则在服务端保留，客户端看到稳定错误语义和编号。若把全部异常堆栈直接发送，调试虽然方便，却会把实现细节变成公开接口的一部分。若只发“失败”两个字，又让用户无法决定下一步。良好的错误合同在可行动解释与内部细节之间建立明确边界。
