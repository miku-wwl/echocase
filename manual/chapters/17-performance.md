# 第 17 章 从实际 EF 查询读懂 PostgreSQL 执行计划

“增加索引会变快”不是足够的工程结论。需要先确定应用真正发出了什么 SQL，再解释索引改变了哪部分工作，最后限定测量结果能支持什么。EchoCase 的查询观察取自实际 Store.ListAsync，而非手写一条看起来相似的简化查询。

## 17.1 查询形状先决定问题

{{code store-list}}

List 按 owner 筛选调查，按 UpdatedAt 倒序取前五十个，再加载发现和关系。实际 SQL 把根选择放在子查询中，外层 LEFT JOIN 两个集合，并为物化增加排序。下面仅摘出根选择部分，保留真实参数名。

```sql
FROM "Investigations" AS i
WHERE i."OwnerId" = @ownerId
ORDER BY i."UpdatedAt" DESC
LIMIT @p
```

该次参数为 owner `probe-owner-17`、limit 50。若把 LIMIT 放到连接后的行上，就可能截断同一根的子项，不能保证取到五十个完整调查。EF 的子查询形状正是为了保留根数量语义，因此比较性能必须使用这个真实结构。

映射已有 (OwnerId, UpdatedAt DESC) 复合索引。观测比较的是已有设计的机制，不是本轮给产品新加了优化。QueryProbe 通过拦截真实 DbCommand 取得 SQL 和参数，再交给 EXPLAIN；正文只保留解释所需的数值与图形。

## 17.2 三种路径各做了什么

{{figure query-plans}}

无 owner 索引时，代表计划顺序扫描三万条根，过滤掉 29,700 条，留下该用户的三百条，再用 top-N heapsort 选出五十条。LIMIT 减少输出，不代表扫描器事先知道哪些是最新的五十条，候选仍需要检查。

只有 OwnerId 索引时，Bitmap Index Scan 与 Bitmap Heap Scan 能找到该 owner 的三百条，减少无关根的读取。但位图访问结果不按 UpdatedAt 排列，所以仍需排序，根数量较多时这部分工作不会凭索引存在而消失。

复合 B-tree 的前导 OwnerId 用于等值范围，后续 UpdatedAt 顺序直接满足该范围内的倒序需求。Limit 得到五十个根就能停止继续读取这个范围。它同时服务过滤、顺序和早停，比“分别建两个索引”更贴合这项查询。[多列索引](https://www.postgresql.org/docs/17/indexes-multicolumn.html)、[索引与排序](https://www.postgresql.org/docs/17/indexes-ordering.html)

## 17.3 根选择变快，外层工作仍存在

复合索引的代表计划中，根 Index Scan 输出五十行。Links 的索引访问执行五十次，每次一条；Discoveries 的索引访问也执行五十次，每次两条；最终连接输出一百行。这里的 Actual Rows 要结合 Actual Loops 阅读，不能把“每次一行”当成整个查询只处理一行。

外层仍出现 Incremental Sort，因为完整排序还包含根 Id 与发现键。根选择分支不再有独立的时间排序，并不意味着整个 SQL 树没有任何 Sort。性能解释应指向具体节点，避免把局部改善扩大为完整查询重构。

执行计划中的 cost 是规划器估算单位，不是毫秒；EXPLAIN ANALYZE 的 actual time 则来自实际执行。父节点覆盖子工作，不能把所有节点时间简单相加当成总时间；BUFFERS 也要注意层级和重复计数。[阅读 EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html)

## 17.4 数值只在测量条件中有意义

{{figure query-cost}}

| 索引条件 | 七次执行时间的中位数 | 可以解释的主要变化 |
|---|---|---|
| 无 owner 索引 | 4.037 ms | 扫描大量无关根后选前五十 |
| 只有 OwnerId | 1.808 ms | 缩小候选，但仍需按时间排序 |
| OwnerId + UpdatedAt DESC | 0.929 ms | 按用户和顺序提前取得五十根 |

数据来自 PostgreSQL 17.7 的一次真实应用表观察：三万根、一百用户、每用户三百根，总计六万条发现和三万条关系。每组先暖身一次，再取七次暖缓存数据，按固定顺序比较；没有并发写入，也没有真实生产分布。

这些数值支持“在此查询形状和样本中，复合索引减少工作”的解释，不能证明生产 P95、API 端到端延迟或最大吞吐。数据库执行时间没有包括完整网络往返、JSON 序列化、浏览器渲染和用户思考。一个漂亮比例若脱离范围，比不测量更容易误导决策。

## 17.5 为什么不继续增加所有可能的索引

索引需要存储和维护，写入时可能增加工作。当前 UpdatedAt 每次成功操作都改变，因此复合索引也随业务写入维护。是否值得，需要看列表读取收益与写入成本，而不是只看一次查询减少了几毫秒。

如果列表只需要标题、状态、计数和最后修改时间，未来可以引入专门摘要投影，减少正文和完整子集合。那会改变查询与前端合同，属于另一项可评审优化。当前章节没有把可能方案伪称成已实现成果。

性能研究的可靠输出是因果模型：哪些行必须访问，何处能提前停止，什么结构造成重复，哪项上限支持当前简化。当数据分布和需求改变，工程师可以用这个模型重新判断，而不是机械复制一组历史数字。

## 17.6 从索引次序推导早停条件

设索引按 owner 分组，每组再按 UpdatedAt 倒序排列。查询固定 owner 时，可以进入这一组，从最新位置依次取得五十条；不必先遍历其他 owner，也不必看完本组才知道前五十。这个顺序推理解释了为什么列次序要与等值筛选和排序一起考虑。

如果查询取消 owner 条件，现有复合索引并不天然提供所有用户共同的 UpdatedAt 顺序，因为第一关键字仍是 owner。若查询按另一个字段排序，也不能仅凭索引包含时间就期待相同收益。索引服务于具体访问模式，不是一个“更快存储”的通用标签。

如果大量记录拥有相同 UpdatedAt，当前列表对根的选择没有稳定分页次序。增加 Id 作为排序与游标组成部分，会同时改变查询和索引设计。性能与合同再次相遇：先明确结果次序，再决定如何高效取得它。

## 17.7 计划是解释，不是固定模板

规划器会依据数据统计、选择率和可用路径改变策略。某个样本中选择 Bitmap Heap Scan，不表示只有 owner 索引时永远只能走这一节点；数据更少或分布不同，可能出现其他合理计划。观测的价值在于能解释这一次为何减少候选和排序，而不是把节点名称背成规则。

暖缓存样本中读块多为命中，不代表没有存储访问成本，更不代表冷启动相同。固定比较顺序也可能引入缓存与环境偏差。若要支撑更广的性能决定，需要不同数据分布、交错测量或实际负载；当前教材停在应用查询机制，不把有限观察包装成容量规划。
