# 第 14 章 TanStack Query 与单调确认缓存

服务器状态缓存并非把最后到达的 JSON 存起来。网络可能让旧查询晚到，幂等重放可能返回旧成功，后台刷新可能在用户编辑时取得新版本。Query 管理请求生命周期，EchoCase 还要定义哪些结果有权更新当前事实。

## 14.1 查询键属于资源身份

{{code query-get}}

键为 ["session", owner, id]，包含用户与调查标识。查询函数消费 AbortSignal，再把它传给 request/fetch。三十秒轮询与窗口聚焦刷新让页面有机会得知其他窗口修改，但不是实时推送；用户仍可能在两次读取之间基于旧快照作决定。[查询键](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys)

缓存不能替代服务端授权。owner 进入键是为了隔离浏览器中的快照，服务端仍按可信身份筛选资源。登录和登出还会清除非 me 缓存，避免同一浏览器账户切换后的展示泄露。两个边界相互配合，而非互相替代。

## 14.2 “后来到达”不代表“后来发生”

{{figure late-get}}

旧 GET 可能在 mutation 开始前发出，结果却在新写成功后回来。如果直接覆盖，页面从版本 5 倒退到 4。取消旧查询能减少这个窗口，但取消需要底层真正使用 signal；即使取消生效，也还存在旧回执等无法用同一种方式消除的结果。

{{code query-latest}}

latest 比较资源版本，保留更高版本。它作为 structuralSharing 处理查询结果，也用于 mutation 成功后的 setQueryData。这样，相同资源键中的确认版本不会因晚到旧结果而倒退。这个保证依赖版本在同一调查身份内单调前进，以及响应符合合同；它不是对任意内容冲突的通用合并算法。

版本相同时当前函数接受 incoming，没有逐字段证明两个同版快照内容一致。正常业务协议应让相同版本代表同一已确认状态；如果出现同版不同内容，应调查写路径是否绕过了版本推进，而不是让缓存临时猜测哪个字段更可信。

## 14.3 mutation 是一段生命周期

{{figure query-cycle}}

{{code query-mutation}}

onMutate 先等待 cancelQueries，避免旧读取轻易覆盖后续确认。mutationFn 发原 Operation。onSuccess 把响应按版本单调合并到确认缓存。onSettled 再使当前调查和总览失效，并 await 两项刷新；mutation 仍保持 pending，直到这些回调的 Promise 完成。[取消查询](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation)、[写后失效](https://tanstack.com/query/latest/docs/framework/react/guides/invalidations-from-mutations)

等待刷新有实际交互效果。LinkEditor 通过 mutateAsync 保存，在 Promise 完成后关闭；如果只“发起刷新”就立刻关闭，用户可能看到旧关系短暂出现，或在列表尚未确认时进行下一项操作。这里把完成时机扩展到必要的确认读取，降低这种界面歧义。

失效不表示所有缓存立即都被重写。活跃查询会按库的规则获取，无活跃观察者的查询也有各自生命周期。当前正在显示的调查具有观察者，因此它是关键确认路径；总览前缀失效则使对应用户列表在需要时重新读取。应按真实使用方式解释行为，避免把 invalidate 当成跨应用同步广播。

## 14.4 为什么不把草稿乐观写入缓存

在发送笔记时直接 setQueryData(notes = draft) 看起来响应迅速，却会让 Query 中同时存在“可能提交”和“已确认”的数据。失败回滚还可能覆盖用户在等待期间刚输入的新内容，尤其多个请求或 refetch 交错时，快照恢复的前提非常脆弱。

{{code notes-pending}}

EchoCase 将正在保存的 operation.body 作为局部提示投影。输入框继续显示 draft.text，确认缓存仍是服务器事实。这保留了及时反馈，却不需要把未经确认的值伪装成持久结果。“乐观”因此不是只有改缓存一种实现方式，关键在于用户能否分辨事实与尝试。

## 14.5 读取失败与未知写入是不同状态

若轮询失败，页面可以保留最后确认快照并展示读取错误，不能据此说本地草稿已失效。若写入结果未知，blocked 则阻止产生新的不同写意图，并提供原样重试。查询的自动重试一次与 mutation 的 retry false 也因此具有不同理由。

一次普通读取可以重复，不会再推进领域版本；自动重复命令则必须保证同一意图。当前选择显式让用户重试未知写入，原 variables 不变。更复杂的离线队列可以另行设计，但不应该在没有持久化意图协议时，仅把 retry 设置为 true 就宣称可靠恢复。

## 14.6 确认缓存与草稿之间还差一层语义

即使 Query 永不倒退，也不能直接把每个新 Session.notes 填回输入框。用户可能有基于旧版本的脏草稿，或者在自己的保存等待期间继续编辑。缓存解决“已确认事实的先后”，草稿钩子解决“这个事实能否确认我手上的输入”。

资源版本 Version 追踪服务器，revision 追踪本地输入代次；只有同时理解它们，才能正确处理晚到成功与后台变化。进入草稿模型前，还需明确刷新失败与操作完成对缓存意味着什么。

## 14.7 失效刷新失败时，哪些事实仍然成立

命令已经得到成功响应，说明这次持久决定成立；随后 GET 失败，不会把该提交撤销。缓存可能暂时保留命令返回的确认快照，并显示读取错误。它仍是可信的历史事实，只是不保证此刻没有更新版本。

若成功结果来自旧回执，而当前缓存更高，latest 保留高版。刷新失败也不能成为倒退的理由。界面需要分别理解“原操作确认了”和“最新读取暂时失败”，避免把后者文字误写成原保存一定失败。

Query 的后台状态能说明请求是否正在获取，却不能回答草稿能否重设基线。这个判断继续由草稿钩子拥有。将所有 isFetching 都当作编辑禁用条件，会让三十秒轮询不断打断用户；将所有刷新结果都直接写输入框，则会破坏输入。

## 14.8 操作完成边界影响组件行为

LinkEditor 的 await 依赖 mutateAsync 返回 Promise，而 Promise 的完成包含实际回调生命周期。当前 onSettled 返回失效刷新的 Promise，因此表单直到必要确认结束才关闭。若未来把回调改成 void fire-and-forget，编辑器源码即使一行未变，用户看到的完成时机也会改变。

这说明可维护性不仅是类型签名。一个 Promise 在何时完成，是跨组件合同；取消是否向下传，是查询合同；版本是否可单调比较，是缓存合同。重构这些位置需要保留语义，并针对实际交互反例验证。

当前 useInvestigation 对同一工作台的一项 mutation 提供 blocked，减少重叠不同命令。它没有跨标签页协调本地锁，也没有取代数据库仲裁。浏览器层减少歧义，服务器层保证事实，两种职责仍保持清楚。
