# 第 9 章 PostgreSQL MVCC 与读取事实的时间

两个请求都读到 Version 4，随后一个成功、另一个失败，并不矛盾。读取回答“在这个快照中看见什么”，写入回答“现在能否让这项决定成立”。MVCC 为并发读取提供版本可见性，应用仍需建立自己的业务写入条件。

## 9.1 行更新留下版本，不是覆盖一张共享纸

{{figure mvcc-tuples}}

可以把一次 UPDATE 理解为创建新的物理行版本，并让可见性规则决定不同快照应看到旧版还是新版。图中的 xmin、xmax 和事务 T0、T1 是概念标识，用来说明版本来源与失效关系，没有声称实际采集了这些系统列。真实事务状态、快照与可见性判断比单纯比较两个数字更复杂。[MVCC 概念](https://www.postgresql.org/docs/17/mvcc-intro.html)

旧快照不能看到尚未提交的 T1 新版本，新语句在 T1 提交之后可能看见它。这样，读者不需要等待每一个写者完成才能读取一个一致的已提交世界。并发写入同一行仍可能等待锁，DDL 也可能与读取发生锁冲突；“普通读写并发更好”不等于数据库没有锁。

应用 Version 则是 Investigation 的业务坐标。Version 从 4 到 5，由根方法显式推进；数据库事务编号属于数据库内部，不与它一一对应。一次事务可能修改许多实体，一次业务版本也可能伴随多个表写入。把 xmin 当作当前应用 Version，会混淆持久实现与公开合同。

## 9.2 Read Committed 的快照属于语句

PostgreSQL 的默认 Read Committed 中，一条普通查询看到语句开始前已提交的数据以及自身事务的相应变化。下一条语句开始时可以取得更新快照。因此把两次 SELECT 放进同一事务，并不能保证它们返回完全相同的事实。[隔离级别](https://www.postgresql.org/docs/17/transaction-iso.html)

{{figure mvcc-statements}}

这对 EchoCase 有两个直接影响。首先，Graph 通过 AsSingleQuery 把根、发现和关系作为一条 JOIN 查询加载，避免在多个读取语句之间拼出不同提交时刻的图。其次，同键重试等待 advisory lock 后，再执行回执查询，可以看到先前事务已经提交的回执；事务是在等待之前开始的，并不因此永久停在旧快照。

{{code store-lock}}

BeginTransactionAsync 没有显式指定更强隔离，实际 Store 竞争观察记录两方都为 ReadCommitted。理解这项事实后，才能解释为何锁等待之后的查询能恢复成功结果，也才能知道图读取与后面的回执读取并非整个事务共享的永恒快照。

## 9.3 单语句图读取的代价

AsSingleQuery 让同级集合通过 JOIN 返回。若一个根有 d 条发现和 l 条关系，连接可能为该根产生 d×l 行，根列在其中重复。当前案件最多六条发现、十五条关系，所以最坏数量受控；这种已知上限支持了选择，而不是让笛卡尔放大现象消失。[单查询与拆分查询](https://learn.microsoft.com/en-us/ef/core/querying/single-split-queries)

若改为 split query，通常能减少重复根列，但多个语句在 Read Committed 下可能观察到不同提交阶段。要保持同样读取语义，可能需要更强隔离或其他设计。不能只根据某个性能提示统一改成拆分，然后认为业务快照保证完全不变。查询性能和一致性经常由同一个选择共同决定。

在实际查询探针中，每个样本根有两条发现和一条关系，五十个根最终形成一百条连接行。这个数字是给定数据形状的结果，不能推广成所有调查永远只放大两倍。第十七章会沿着真实计划解释根选择和子表连接分别花费什么。

## 9.4 可见性不会阻止丢失决定

设 A、B 都读取版本 4，各自计算版本 5。若最后只是按 Id 更新，后提交者可能覆盖先提交者的结果。两个事务都只读了已提交数据，仍然会丢掉一个用户决定。MVCC 防止看见半提交世界，不会自动知道这两个决定是否可以合并。

EchoCase 把加载时的 Version 作为 UPDATE 条件，并让任何成员修改都推进根。第十章将说明数据库等待之后如何重新判定条件，以及 EF 如何根据影响行数报告竞争。这里先建立边界：读取隔离提供观察基础，业务并发协议保护决定，二者解决的问题不同。

## 9.5 跨行规则暴露更大的边界

{{figure write-skew}}

值班反例不是 EchoCase 新增功能，而是帮助识别当前策略的适用条件。A 和 B 都看到两人值班，各自只更新自己的行；如果每行版本都未改变，各自 CAS 可能通过，最后却没有任何人在岗。每行更新都合法，并不推出跨行约束仍成立。

如果规则跨越多个聚合，可以让决定竞争一个共同锁定点，或在适当设计中使用 Serializable，并处理整个事务重新执行。提高隔离不能省略失败处理：序列化失败意味着这次决定需要在新事实下重做，而不是只重试最后一条 UPDATE。是否可以自动重做，还要看其中是否包含外部副作用和用户选择。

当前调查把需要同步判断的发现与关系收在一个根版本下，缩小了这种风险；它没有宣称解决任意跨调查规则。清楚认识边界，才能在新需求出现时知道什么时候需要改变模型。

## 9.6 事务生命周期影响读取成本

旧快照需要旧行版本继续存在，长事务可能让旧版本的清理推迟。读事务看起来没有改数据，仍可能对系统产生持续成本。本书不把它扩展成运维教程，只保留应用设计含义：不要把等待用户输入、远程交互或长时间计算藏进数据库事务。

EchoCase 的事务在收到完整命令后才开始，数据库读取、领域决定和保存处于有限请求链中。用户在浏览器编辑数分钟，不会持有一个同步数据库事务；她只持有 baseline Version。乐观并发把这段思考时间移出数据库，把重新确认放到冲突发生时；继续理解快照和对象缓存，才能看清这项选择的条件。

## 9.7 快照判断不只是比较大小

一个容易误导的心智模型是“xmin 小于当前事务号就可见”。事务可以交错开始和提交：较早编号的事务仍在执行，较晚编号的事务却已经提交。快照需要识别在它建立时仍活跃的事务，并结合提交状态判断行版本；仅看事务号先后不足以恢复可见世界。

{{figure mvcc-visibility}}

图中 T1 和 T2 都是示意，重点是提交边界。快照建立时 T1 尚未提交，即使稍后真的提交，这个旧快照也不会因此改写成新快照。下一条 Read Committed 语句可以取得新快照，从而看到 T1 的结果。于是“不读未提交”与“可重复读”成为不同保证，不能混用。

数据库语句内部也不要求在整个执行期间停止其他事务。它依据确定的可见性规则遍历版本，其他事务可以继续提交。应用得到的是一个自洽读取视角，而非暂停世界后的拍照。这种理解比“先锁全表再读”更接近 MVCC 的目的，也更能解释长快照为何仍需要旧版本存在。

## 9.8 EF 身份缓存可能遮住新快照

即使数据库下一次查询使用新快照，跟踪上下文仍可能复用已经管理的同键实例。数据库可见性和 EF 对象身份是两层机制：前者决定语句能读到的行，后者决定结果如何进入当前对象图。不能拿一个长期跟踪的对象一直不变，直接证明 PostgreSQL 提供了事务级重复读。

EchoCase 的 Get 使用无跟踪查询，Write 每个请求使用新上下文，因此当前路径减少了这种混淆。在研究隔离级别时，要明确观察的是原始 SQL 结果、重新物化的对象，还是同一个跟踪实例。否则实验可能无意中研究了身份映射，却把结论写成数据库隔离。

同样，前端 Query 的最后确认缓存也不自动等于数据库的“最新”。从数据库快照到 EF 对象，再到 HTTP 正文和浏览器缓存，每层都可能保留一个有限时刻的事实。版本使这些时刻可以比较，却不会让传播延迟消失。

## 9.9 更强隔离解决什么，又留下什么

Repeatable Read 让事务中的后续读取保持更稳定的快照，因此适合需要同一观察世界的分析，但不能仅凭它就宣称所有跨行业务约束安全。前面的值班写偏差正说明，两个事务在同样稳定的旧世界中分别改不同的行，也可能共同违反规则。

Serializable 追求与某种串行顺序等价的成功结果，代价之一是部分事务必须失败重试。失败不是数据库“不稳定”，而是系统拒绝让不可能串行成立的决定共同提交。应用需要重新读取并重新计算整个决定；若其中包含已执行的外部副作用或不可重复用户选择，自动重试又需要额外设计。

EchoCase 当前选择默认隔离、单语句图读取、同键事务锁和根条件写入。这些机制各自负责一个边界，并没有把事务级别作为万能替代。评审时，应沿实际可能的竞争列出保护点，再判断是否存在未被任何一点仲裁的规则。
