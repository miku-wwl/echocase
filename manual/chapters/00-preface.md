# 序言：把一次保存解释清楚

调查员在笔记框里输入一句话，按下“保存”，然后继续补充另一条线索。网络稍慢，服务器先保存了第一句话，响应稍后才回来。此时，输入框应该显示什么？页面能否写“已保存”？如果另一个窗口又修改了档案，第一次保存的成功响应还能覆盖当前界面吗？

这些问题把企业应用的几个核心困难放在同一张桌上：业务对象如何表达允许的变化，数据库如何保证多项变化一起成立，HTTP 如何区别过期决定与重复尝试，前端如何保留用户尚未交付给服务器的意图。只有沿着整条路径追踪，才可能解释一个看似普通的按钮究竟承诺了什么。

本书以 EchoCase 的实际实现为主线。它是一个体量受控的调查档案应用，使用 C#、ASP.NET Core 10、EF Core 与 PostgreSQL，前端使用 React 19、TypeScript、TanStack Query 和 React Flow。案件题材让证据解锁、关系判断、调查复核和结论封存自然形成规则，读者不需要先学习复杂行业知识，就能进入一致性和交互语义。

## 如何阅读这本书

前六章从需求和领域进入请求、用例与 HTTP 合同。第七至十一章深入持久化：对象跟踪、兼容演进、MVCC、乐观并发和幂等。第十二章把可信身份、资源所有权与防伪校验接回同一条业务路径。第十三至十六章走到浏览器，解释渲染快照、确认缓存、草稿代次和图谱状态。最后几章讨论真实查询计划、验证边界、需求演进以及带解析的设计题。

每章的源码框来自明确固定的应用版本，显示真实路径和行号，链接可以直接定位上下文。为了在书页上阅读，超长行会折行，续行不生成新的源码行号。图中的时间轴强调因果次序，不按真实耗时比例绘制；示意事务编号和版本值会与真实观察明确区分。书中的运行摘录只保留能帮助推理的部分，不能用小段 SQL 代替整份实际查询。

正文不要求读者逐条执行命令。理解一次并发失败，并不以亲自建立数据库、收集日志和整理测试记录为前提。需要进一步研究时，可以从代码框进入实现，从章节给出的测试符号进入反例。本书让实现、图示和解释互相校正：当一句抽象原则无法说明实际源码的行为，就应缩小结论或重新理解机制。

## 真实系统，也有明确边界

EchoCase 只有一个固定案件定义、六条证据和至多十五条无向关系。读写共用一个 PostgreSQL 数据库，没有消息总线、独立读模型或外部通知。它使用逻辑 CQRS 与有行为的聚合，不以框架数量证明“企业级”。本书所说的企业应用工程，指对规则、身份、一致性、失败和可维护性的认真处理。

读者会看到仍需保留的限制：回执没有自动到期策略，草稿没有跨页面持久恢复，图谱位置只在当前视图中保留，账户功能也不构成完整的企业身份治理。这些限制有助于判断设计适用的条件。把样例中尚未实现的能力写成现有保证，会破坏理解，比承认范围更危险。

正文的源码固定于四目录整理后的应用提交 `908811b95fb40cf14fa79b8eddf41796aa02cc04`。界面与数据库观察选自 2026 年 11 月 11 日的真实运行；本轮对照确认，相关应用源文件在目录迁移后保持相同内容，只有路径与换行形式存在机械差异。这些是历史运行观察，不是对任意环境、负载或未来版本的承诺。详细素材出处保存在教材源的参考目录，读者不必在正文中穿行于记录清单。

## 一条贯穿全书的判断标准

理解框架，意味着能预测边界情况，而不仅能复述通常路径。读完 EF 章节，应能解释为什么修改子对象之后根版本也必须进入 SQL 条件；读完幂等章节，应能解释为何重试必须保留旧版本；读完 React 章节，应能解释为什么成功响应不能随意清空输入框的 dirty 标志。

本书会反复追问：当前掌握的事实来自哪个时刻，正在表达的是哪一次意图，哪一层有权作出这个决定，失败后还能相信什么。答案将具体落在对象、语句、事务、响应和屏幕上。把这些因果联系起来，才是一次保存真正完成的含义。
