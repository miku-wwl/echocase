# 第 18 章 用反例验证承诺，而非累积测试数量

测试最有价值的部分，是把容易被忽略的时间与边界变成可观察条件。一个测试通过，不代表系统所有性质都成立；一个有因果设计的反例，则能说明某项机制为什么必要。EchoCase 的独立测试分别观察领域决定、真实 PostgreSQL 事实和浏览器交互，不把它们混成一种“运行成功”。

## 18.1 先确定要推翻的错误假设

若假设“修订关系就是删除后重建”，测试应检查身份和端点保持；若假设“收到成功就能清 dirty”，测试应让用户在响应返回前输入下一代文本；若假设“版本 if 检查已经足够”，测试应强制双方都在数据库保存前读到旧版本。

{{figure test-reasoning}}

这样的测试由反例驱动，而不是把每个方法再调用一遍。它们需要明确的观察点：对象是否在失败后保持旧值，事务是否只留下成功回执，输入框是否仍有新文本。状态码和截图可以参与解释，却不能替代所有关键事实。

## 18.2 单元边界检验规则与身份

{{code unit-revision}}

这个实际测试先保存关系身份与版本，再修订，断言 Id、InvestigationId、SourceId、TargetId 不变，类型、解释和时间变化，根版本只推进一次。它还立即重复相同修订，要求得到 link_unchanged 并保持版本。这样同时区分有效变化与无意义重复。

{{code unit-unicode}}

边界用例使用一个在 UTF-16 中占两个 code unit 的字符，覆盖十九、二十、五百和五百零一个标量值。若把 EnumerateRunes 改为 Length，测试会直接挑战业务单位，而非只证明普通汉字可通过。固定时间也让断言不依赖真实等待。

单元测试不能证明 PostgreSQL 的 CHECK 接受同样内容，也不能证明 EF 把子关系标为 Modified。它没有数据库，正因此快速且清晰；跨到持久机制的结论需要另一个边界。

## 18.3 集成验证必须触及真正的竞争窗口

{{code integration-race}}

每次 Attempt 使用独立上下文。屏障位于 Store 已加载聚合之后、领域变更之前，要求双方都走到同一个窗口。不同键排除同键重放的影响，再断言只有一个成功、失败为 412，并检查最终关系、版本、回执与审计。

这里使用真实 PostgreSQL，是因为唯一键等待、事务回滚、READ COMMITTED 与生成 SQL 都属于数据库行为。内存替身可以验证方法被调用，却不能证明这些竞争性质。WebApplicationFactory 可以替代 HTTP 宿主，不意味着数据库也应该换成内存提供者。

迁移验证同样需要旧列集中的真实数据，以及旧 JSON 回执。只在空库执行最新模型，会漏掉“旧行保持身份”和“缺少新字段仍可反序列化”两个承诺。验证对象应随兼容对象变化，而不是总从干净世界出发。

## 18.4 浏览器反例要控制因果，少猜时间

{{code e2e-delay}}

route.fetch 先让真实 API 执行并提交，再延迟把响应交给页面。测试随后让输入框继续编辑，最后释放响应。这与直接伪造一个成功 JSON 不同：事务确实发生，只有交付时间被控制。另一项反例在真实提交后截断正文，用来研究成功状态与可解析结果之间的缺口。[网络拦截能力](https://playwright.dev/docs/network)

等待固定秒数只能猜测环境速度；等待明确的 committed Promise、版本标签或保存状态则描述事件关系。类似地，界面中某段文字可能同时出现在输入框、pending 提示和确认区域，断言“页面包含这段文字”无法证明它已经持久化。应定位正确区域，并在需要时读取真实服务器值。[可等待断言](https://playwright.dev/docs/test-assertions)

这不是把书变成浏览器脚本教程。关键思想是：让被研究的先后关系确定下来，再观察对应事实。若控制条件与结论无关，即使脚本跑得很稳，也没有验证想要的承诺。

## 18.5 测试依赖边界保护生产系统

Unit 只引用 Domain/Application，Integration 可以引用实际 API 与持久层，E2E 通过公开界面交互。生产项目不能引用测试项目或夹具；Playwright 安装在独立 test/e2e 包中，不进入前端生产依赖。应用解决方案不包含测试项目。

验证应从多个方向观察：项目引用描述显式结构，求值后的 MSBuild 项目图揭示条件导入，解析后的包图揭示传递依赖，实际发布目录和浏览器 bundle 揭示产物。它们各自能发现另一层看不到的问题，却不需要把实现这些检查的脚本印进教材。

data-testid 只是可测试属性，并不等于把测试运行器打进生产。反过来，没有 test 字样也不保证依赖正确。边界根据实际来源和依赖关系判断，避免把命名当成架构事实。

## 18.6 回归保护与设计演进

重构时优先保留外部承诺的测试：身份稳定、失败原子、草稿保留、显式冲突。若测试只断言私有函数调用顺序，内部拆分就会造成无意义失败；若测试完全不观察持久结果，破坏事务也可能悄悄通过。好的验证给合理重构留空间，同时对用户会感受到的回归敏感。

测试总数不进入本书的学习成绩。能解释每个反例推翻了哪项错误假设、还留下哪些未覆盖条件，比重复展示绿色记录更有价值。这些判断还需要独立的观察出口，避免结论和被测实现共享同一个错误。

## 18.7 有效反例需要独立的观察出口

若浏览器测试只看同一个输入框，就无法区分本地仍显示原文与服务器真的保存。独立 Get 读取或确认区域提供另一个观察出口；数据库竞争测试则用新上下文检查持久结果，避免直接相信失败上下文里的对象。

观察出口也必须符合研究问题。验证所有权时，应使用不同身份请求同一实际资源，不能只检查菜单是否隐藏；验证幂等时，应比较原键重放后的版本和持久审计，而不只是两个响应都 200；验证迁移时，应保存旧行身份并跨迁移读取，而不只查看新列存在。

这些做法不是让每个测试都跨越全部系统。它们让一项保证至少有一个不会被同一错误共同伪造的观察。单元规则用独立断言，数据库事实用真实重读，界面承诺用目标区域和服务器结果，各自保持清楚范围。

## 18.8 小而明确的持续验证

持续验证执行应用构建、独立测试、合同和依赖边界。它负责尽早发现应用回归，不拥有环境发布和基础设施运行。出版工具也不被塞进生产依赖；教材更新可以独立完成版式与编辑检查。
