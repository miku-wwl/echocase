# 第 5 章 用例服务与逻辑 CQRS

CQRS 最直接的价值，是让“想知道什么”和“想改变什么”有不同语义。查询可以被取消、缓存和重复读取；命令携带用户决定，需要判断合法性、版本和重复尝试。EchoCase 让两者使用不同方法和请求类型，但读写仍共用数据库与返回视图。理解这个具体范围，比先决定引入哪种分派库更有帮助。

## 5.1 一个服务协调什么

{{figure usecase}}

InvestigationService 的方法名对应用户意图：Start、Examine、Link、ReviseLink、Notes、Transition、Verdict。每个方法构造所需参数，再通过共享 Write 建立变更上下文。它没有直接保存数据库，也不在自身复制完整领域状态机。

{{code app-revise}}

ReviseLink 把 linkId 与 body 一起纳入操作内容，操作名固定为 revise-link。回调在 Store 完成加载和协议检查后才执行；此时 i 应当是可信 owner 范围内的调查。回调把字符串枚举转成领域枚举，并调用根方法。这个端口让应用服务表达要做什么，把事务何时成立交给持久层。

PUT 修订端点要求 Kind 精确等于枚举名称。Enum.TryParse 可能接受数值形式字符串，所以额外的 ToString 比较具有实际意义。现有 POST 建联路径没有这一项比较，仍保留原合同的较宽接受范围。本书把差异写出来，因为维护系统常常需要兼容已有行为；不能为了描述整齐而假装两个入口已经完全相同。

## 5.2 共享写路径是一段协议

{{code app-fingerprint}}

Write 首先要求标准 D 格式的 UUID。随后对包含 id、version、operation、body 的应用对象序列化，再计算 SHA-256。指纹不包含任意原始请求字节，JSON 属性空白或 HTTP 头顺序不决定意图身份；但版本、路由语义和正文内容都进入比较。这是当前 DTO 和序列化路径中的规范形式，不是对任意 JSON 的跨语言规范化标准。

Key 的字符串本身会按收到的形式持久化，并没有先统一 UUID 大小写。新客户端生成的新键具有稳定形式，原样重试不会出问题；但不能据此声称所有文字形式相同的 UUID 都自动折叠为一个业务键。要改变这项行为，需要一起考虑旧回执查找和兼容策略。

Change 把 owner、key、fingerprint、sessionId、expectedVersion 和 operation 传给 Store。它不只是一个“保存参数集合”，而是一次用户意图的身份与前提。第十一章会解释，为何重试必须保留旧 expectedVersion，而不能为了通过检查偷偷改用最新版本。

## 5.3 校验分层的理由

{{figure validation}}

API 负责请求能否绑定；应用层负责用例合同的类型转换；领域根负责状态与内容规则；数据库负责持久事实的关系约束及竞争仲裁。它们可以共同约束一条请求，但不必都写相同的 if。客户端的二十字提示是及时反馈，领域中的计数是业务保证，数据库 CHECK 是最终持久约束，各自应与对应单位保持一致。

分层不意味着所有错误都提前发现。例如即使领域已检查无重复关系，另一个请求仍可能竞争相同数据。Store 的事务和根版本承担这一窗口里的判断。若为了避免数据库错误而在应用层先做一次额外查询，仍然没有消除查询与保存之间的竞争，反而可能引入另一个过期观察。

## 5.4 查询模型与命令结果为什么相同

SessionView 是完整调查视图，查询和成功命令都返回它。这样，命令成功后界面可以立即获得新的版本、状态和关系，不必凭请求正文自行猜测服务器规范化后的内容。Trim 后解释、评分和解锁状态，都以服务端视图为准。

相同形状不代表相同时间语义。Get 描述一次读取快照；回执重放返回过去某次命令成功时的 SessionView。这个差别会直接影响前端缓存：旧回执即使 HTTP 200，也不能使确认缓存从版本 8 回到版本 5。CQRS 的主要区分在意图与时间，而不只是 DTO 是否使用不同类名。

当前没有异步投影或读写库分离，因此命令提交后针对同一数据库的新查询可以读到已提交事实，不存在额外消息队列引起的投影延迟。仍然存在网络乱序、并发新写和语句快照差异；“没有最终一致读模型”不等于“所有读取永远最新”。

## 5.5 时间依赖也是用例输入

{{code app-time}}

Service 从 TimeProvider 获取 UTC 时间，并把不足微秒的 tick 尾数去掉，再交给领域。这样，业务对象、命令回执和数据库重读使用可一致表达的时刻。测试可以替换时钟，讨论规则时不必依赖实际等待。

审计和回执自己的 CreatedAt 由 Store 的时钟获取，并非完全同一个局部 now。它们记录相邻的持久操作时刻，不能被当作领域 UpdatedAt 的逐 tick 同义字段。这也是为何数据建模应说明时间字段各自代表哪个事件，而不是只给所有字段起一个“时间戳”的统称。

## 5.6 何时值得拆分更细

如果每个新用例都在服务中复制授权、验证、日志和事务，维护成本会发出信号。可以引入独立处理器或组合行为，但要先确定需要复用的语义。当前共同部分是一个数据库写协议，显式 Write 足以集中处理；领域规则仍各自清晰。

相反，若把每个三行方法拆成请求、处理器、验证器、映射器和注册器，却没有独立变化原因，读者追踪一项业务决定就要跳更多文件。架构粒度应随职责和复杂度增长，不应由术语预先规定。这个小服务展示的是一种有边界的协调方式，而非所有企业项目都必须采用的最终模板。

## 5.7 回调端口的能力与约束

WriteAsync 在完成锁、资源加载和回执检查后调用 apply。回调接收的是本次上下文已加载的聚合，新建调查时才是 null；应用方法在既定路径下使用 i!。这个非空断言不是对任意调用的运行时验证，正确性依赖 Change 与用例入口共同建立的前提。

回调是同步函数，领域决定不在里面等待远程 API。这样，Store 能清楚包住一次有限业务修改，回执重放时也能完全跳过它。如果未来把外部调用或不可重复副作用塞进回调，锁与事务会被拖长，重试语义也会失效。接口签名允许传递代码，不表示任何代码都适合进入事务。

这种设计换来的可读性，是每个用例的领域调用与操作名相邻；代价是应用端口理解一个特定工作单元形状。大量跨聚合操作或复杂异步编排出现时，它可能不再合适。架构评审应保留这些改变选择的信号，而不是把现有简化永久规则化。

## 5.8 规范化发生在指纹之前还是之后

解释的 Trim 在领域内部执行，指纹却根据应用请求对象建立。因此同键请求从“前后有空格的解释”改成“去掉空格的解释”，即使最终领域文本可能相同，也会被视为不同请求而拒绝。这个行为保护了原意图的精确重放，不能被描述成语义等价去重。

若希望把某些差异规范化后再建立指纹，需要明确哪些差异被忽略，以及已有回执如何比较。比如更改枚举大小写接受规则，会同时改变绑定、领域转换和指纹含义。这样的调整属于合同演进，不能当成无关紧要的字符串清理。

共享 Write 的价值正是在一个地方暴露这类决定。所有写方法都携带相同的意图坐标，便于分析重放与冲突；业务规则仍留在根中，避免协议复用演变成通用数据修改器。
