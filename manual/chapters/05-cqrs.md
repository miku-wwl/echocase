# 第 5 章 CQRS、校验与应用编排 {#ch05}

## CQRS 可以从一个明确分工开始

命令表达“希望改变什么”，查询表达“需要看到什么”。EchoCase 的 StartRequest、LinkRequest、NotesRequest 和 VerdictRequest 是命令输入；CaseSummary 和 SessionView 是查询与命令完成后的投影。命令与查询仍然使用同一个数据库，没有读副本，也没有消息总线。这个规模下，读写职责分离已能提供大部分可读性收益。

应用服务负责把可信用户、协议预期和领域动作连接起来，不负责判定哪个人应该为虚构案件负责，也不负责生成 SQL。API 解析 If-Match，应用服务计算请求指纹，领域执行状态规则，基础设施保证原子提交。每层都知道足够完成职责的信息，避免任何一层成为“什么都知道”的对象。

## 校验应该放在哪里

| 校验问题 | 所需知识 | 主要位置 |
|---|---|---|
| JSON 缺字段或显式 null | HTTP 合同 | API 参数绑定 |
| 版本头格式是否合法 | HTTP 条件请求 | API |
| 幂等键是否是 UUID | 用例协议 | Application |
| 证据是否已经调查 | 聚合状态 | Domain |
| 调查是否属于当前用户 | 身份与资源 | 持久化查询边界 |
| 同一对关联是否重复 | 聚合与关系约束 | Domain + PostgreSQL |

重复校验不一定浪费。用户界面限制长度可及时反馈，领域重复检查长度可保护所有调用者，数据库长度限制可保护直接写入。这三层面对不同失败源。应避免的是无意识地把同一套复杂规则复制成三个互相漂移的实现。

## 事务编排与领域行为的分界

领域回调只应修改当前聚合并返回它，不应执行外部网络调用、发送邮件或写另一套存储。事务端口可能因为并发冲突回滚，调用者也可能在提交结果不明时重试。回调含有外部副作用时，即使数据库事务完全正确，也无法证明整个用例原子。

这种限制让本项目可以用简单的本地事务完成当前需求。如果将来提交结论需要通知外部系统，应引入同事务的 outbox 记录，再由单独投递器至少一次发送并在接收端去重。那是新需求驱动的扩展设计，当前没有实现也没有假装验证。

## 取消、超时与错误传播

CancellationToken 从 HTTP 请求传到 EF 的异步调用，避免客户端断开以后继续执行不必要的长查询。取消并不意味着数据库一定没有提交，尤其是在 COMMIT 附近断开。若取消导致结果不确定，客户端仍应使用原幂等键确认，而不是生成新业务动作。

数据库命令超时用于限制一次数据库调用的等待，不等于整个用户操作的总预算。锁等待、连接建立和多个命令可能分别消耗时间。当前教学实现选择较短数据库命令超时，并保持失败明确；它没有实现自适应重试、熔断器或全局限流集群。描述范围时应把这些缺项说清楚。

## 练习与参考答案

**5-A：** 为什么不让命令只返回 204？参考答案：204 可以成立，但客户端随后需要再查询版本和投影。当前返回新 SessionView 与 ETag，方便明确本次提交后的状态；幂等重放返回的则是原始操作快照，可能已经落后于当前数据库。

**5-B：** 新增审计字段应放在领域事件里还是事务端口里？参考答案：取决于含义。业务事实可由领域表达；谁在什么请求中执行了什么操作属于应用审计。无论来源如何，都必须明确持久化原子性。当前审计不保存完整变更前后镜像。

**5-C：** 为“提交后给调查员发送邮件”画出可靠交付方案，并标注哪些部分当前没有实现。参考答案：业务事务写 outbox，独立投递器读取并重试，邮件适配器记录投递结果。不能把“事务内调用邮件 API”当成回滚保证。
