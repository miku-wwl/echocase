# 第 11 章 React 19 与可维护的前端边界 {#ch11}

## 前端架构应沿着状态所有权划分

EchoCase 的页面包括登录、案件总览和调查工作台。工作台再分为证据、图谱、笔记、复核与结论。视觉上它们属于同一产品流程，代码上则需要区分服务端快照、用户草稿、视图选择和节点布局。把所有数据放进一个全局 store，会让保存成功、刷新、注销和切换调查的语义混在一起。

| 状态 | 所有者 | 保存位置 | 何时失效 |
|---|---|---|---|
| 当前用户 | 服务器会话 | Query 缓存 | 注销、会话过期 |
| 调查快照 | 服务器 | Query 缓存 | 成功写入、焦点刷新、定时刷新 |
| 尚未保存笔记 | 当前编辑者 | 组件本地状态 | 明确保存成功或主动放弃 |
| 当前调查 ID | 导航 | URL 查询参数 | 用户导航 |
| 图谱节点位置 | 当前视图 | 组件状态 | 离开视图 |
| 防伪请求令牌 | 会话上下文 | 内存 | 登录/注销后刷新 |

没有把认证票据放进 localStorage。URL 只携带调查 ID，不携带密码、令牌或证据正文。浏览器后退通过 popstate 恢复选中调查；刷新页面后重新加载服务器快照，而不是恢复一个过期的本地 JSON 副本。

## 组件边界与实际规模

当前 App 负责身份切换和页面导航，Dashboard 负责列表与启动，Workspace 负责一份调查的查询和写入生命周期，EvidenceGraph 负责图谱交互，Verdict 负责复核与提交表单。客户端协议集中在 api/client.ts，生成类型在 api/schema.d.ts，官方 shadcn 组件位于 components/ui。

Workspace 仍是较大的组件，这是当前维护性限制。继续增长时，应把证据面板、笔记编辑器和写入 hook 拆为独立模块，并用已有 E2E 保持行为。不能为了立刻达到“组件数量看起来合理”而拆出只有转发属性的空壳；应围绕状态生命周期与交互变化拆分。

## TypeScript 类型是沟通工具

客户端直接引用 OpenAPI 生成的 DTO 类型，减少两端各自维护同名接口的漂移。严格 TypeScript 检查阻止把可能为空的正文直接当成字符串，也曾发现版本号数字合同过宽。类型系统不能验证网络实际返回的数据，也不能证明用户有权限；它帮助开发者在编译期发现一类错误。

请求函数把协议头、Cookie 发送、错误解析和网络失败集中起来。业务组件不拼接密码票据，不直接写 fetch 后忽略 response.ok。把网络错误包装为带状态、机器代码与 trace ID 的 ApiError，使工作台能为不同失败提供不同恢复路径。

源码定位：[client.ts](../../frontend/src/api/client.ts)。

## 表单与可访问性

邮箱、密码、笔记、证据选择和结论说明都有可关联的标签；错误使用 role=alert，保存完成使用 role=status；选项卡具有 tablist、tab 与 aria-selected；图谱提供选择框建立关联的替代路径，不要求用户只能拖拽。这里验证了可通过标签定位的自动化流程，但没有完成全套屏幕阅读器和 WCAG 审计。

shadcn 组件生成到仓库，应用拥有修改责任。生成后的 Button 基于 Base UI，不能假设所有按钮默认都是表单提交按钮；登录和结论提交明确设置 type=submit。依赖组件库不免除理解原生表单行为的责任。

## 登录成功但页面没变化的真实缺陷

首轮浏览器测试中，注册和登录 HTTP 都成功，页面仍停在登录界面。原因是登录回调先清空整个 QueryCache，再用 setQueryData 创建新的 me 查询；现有观察器仍关联被移除的旧查询，未收到新数据。后端测试无法发现这个浏览器缓存生命周期问题。

修正保留 me 查询，只移除其他账户相关查询，再更新当前用户数据。注销采用同样原则，并刷新防伪令牌。这个案例比“调用 invalidateQueries 就能解决缓存”更具体：要理解观察器、查询实例和缓存键的关系，而不只是记住某个方法名称。

## 实验 E11：刷新、导航和账户隔离

创建账户后开始调查，保存笔记，记录 URL，刷新页面，再进入笔记页验证内容。注销后用另一个账户登录，确认前一个账户的调查不在列表中。当前后端越权测试和缓存清理共同保护该边界；不能依赖其中一方掩盖另一方遗漏。

移动端实验使用 390×844 视口，执行登录、启动、调查与图谱展示，并断言文档没有横向溢出。它证明这个具体视口与浏览器下的行为，不等于所有移动设备、缩放比例与辅助技术都已验证。

## 练习与参考答案

**11-A：** 为什么当前调查 ID 适合放 URL，草稿不适合？参考答案：ID 便于刷新和导航恢复，草稿可能敏感、很长且未提交；放 URL 会进入历史与日志，也没有清晰并发语义。

**11-B：** 本地布局是否必须保存到服务器？参考答案：取决于产品需求。当前明确提示布局只在视图保留，关联才是持久业务数据。若增加布局保存，应把个人呈现偏好与调查业务版本分开，避免移动节点造成无意义冲突。

**11-C：** 为工作台提出一项有依据的重构。参考答案：把笔记的 dirty、服务端基线和保存 mutation 提取为专用 hook，同时保留冲突与回滚 E2E。只拆 JSX 而不明确状态所有权，收益有限。
