# 第 18 章 综合考核、证据审查与后续工程 {#ch18}

## 综合任务：解释一个操作的一生

选择“提交结论”作为考核场景。先从浏览器表单追踪请求正文、Cookie、防伪头、幂等键和 If-Match；再找到 API 绑定、应用指纹、资源加载、领域 Submit、EF 状态变化和数据库事务。最后从新页面读取封存结果，说明哪一步证明持久化、哪一步只是内存状态。

合格答案不应只画四层框。需要解释复核状态为什么被冻结，支持证据为什么必须来自已发现集合，重复请求为什么不会重复提交，另一个账户为什么不能重放回执，数据库断开时客户端如何判断结果未知。能把这些边界连起来，才体现完整的软件工程能力。

## 考核一：受控故障排查

给考生三种症状，要求先收集证据再修正：登录 API 返回 200 但页面仍停留；没有其他用户却出现 EF 并发异常；数据库暂停时业务返回 500。对应本项目真实发现的缓存观察器、主键生成映射和包装异常问题。

评分不以“猜中某个关键词”为准，而是检查能否提出可证伪假设、选取最小实验、解释反例并在修复后重复相同场景。修正后只跑一次不相关单元测试，不足以证明缺陷已闭合；修改错误映射后应再次真实断库。

| 能力 | 观察行为 | 不充分的替代物 |
|---|---|---|
| 领域建模 | 能用状态机解释非法动作 | 只列实体名称 |
| 一致性 | 能说明数据库原子边界 | 只说使用了事务 |
| 全栈恢复 | 保留草稿并处理旧版本 | 自动覆盖冲突 |
| 安全 | 从可信身份过滤资源 | 隐藏按钮或随机 ID |
| 性能 | 控制变量并读执行计划 | 单次秒表或固定倍数口号 |
| 可靠性 | 区分注入、观测与恢复口径 | 容器 Up 截图 |

## 考核二：维护性变更分析

提出需求：“结论可以被撤回一次，撤回后允许继续调查。”先列语义问题：谁能撤回、何时允许、原分数与支持证据是否保留、审计如何表达、撤回后幂等重放应返回什么、其他窗口看到封存版本时如何恢复。然后才讨论枚举和端点。

当前实现没有该功能。考生应提交设计与测试计划，或在独立分支完整实现并提供新证据；不能直接删除只读检查。一个看似小的状态边会同时影响领域、数据库 CHECK、API、前端交互与教材说明，是维护性评审的理想练习。

## 考核三：审查一个“全绿”报告

审阅者拿到 TRX、Playwright JSON、SQL 计划、恢复结果、容器结果、PDF 和验收报告。首先核对它们是否来自同一代码与版本，再检查是否存在跳过测试、空集合通过、坏输入返回零、缺失文件、无来源数字或未标记的模拟。

自动门禁能检查文件存在、摘要、结构化结果、来源绑定的数值和章节代码片段边界。它无法理解所有自然语言推论，因此还需要逐条审查重要结论。例如“启动后 79 ms 可读”与“RTO 为 79 ms”只差几个字，证据支持程度却不同。

## 发布验收如何分层

工程验收检查应用、数据库、浏览器、容器和实验；出版验收检查目录、链接、图意、代码、可读性与逐页视觉；外部审阅检查教学是否适合目标读者。三者没有一个能自动代替其他两者。

本书是 review edition。页数按实质内容和版面生成，不通过重复日志、空白页或放大字体凑成目标。验收报告给出实际页数与原定 300–400 页目标的差异，并标明后续编辑、外部读者反馈和生产验证事项。若某个目标未完成，就保留 PARTIAL，不把它包装成已满足全部最终条件。

## 继续深化的优先级

优先补齐能改变当前使用风险的工作：账户恢复与会话撤销、复杂冲突差异界面、证据目录版本、查询分页、回执保留、备份恢复与指标导出。随后基于实测决定是否懒加载图谱、是否使用查询投影、是否需要更细功能模块。

仍然不需要为了简历标签增加微服务、Kubernetes、AI 代理或多租户。每一项新技术应对应一个不能由现有方案合理解决的需求，并能用实验解释收益与代价。工程深度来自理解边界和失败，不来自部署组件数量。

## 练习与参考答案

**18-A：** 给本项目最强的一项证据与最弱的一项承诺各举一例。参考答案：真实双窗口冲突加数据库状态核对是较强证据；“生产就绪”没有长期运行、账户治理、灾难恢复与云环境证据，不能作为已实现承诺。

**18-B：** 如何让独立验收更独立？参考答案：由未参与实现的人在干净环境按文档复现，使用独立验收问题与故障注入，记录与作者解释不一致的结果。当前独立成册报告不等于第三方审计。

**18-C：** 在完成学习后写一页个人复盘，分别说明你亲自执行、阅读推导和仍未验证的内容。参考答案应有明确范围与来源，不把作者在本机执行的实验描述成自己的生产经验。
