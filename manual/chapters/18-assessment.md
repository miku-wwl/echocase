# 综合应用工程评审

先让一个新开发者按README恢复依赖、连接本地PostgreSQL、迁移、启动API/Vite，再运行独立UnitTests、IntegrationTests和E2E。审阅对象是实际规则、数据、状态与依赖，不是工具数量。

| 问题 | 可以支持结论的检查 |
|---|---|
| 领域规则是否集中 | 根行为与纯单元反例，失败后版本不推进 |
| 子关联能否局部提交 | 两个跟踪上下文/Store竞争，真实数据只剩胜者，回执和审计同事务 |
| 原键是否安全确认 | 重放不推进版本，改意图409；旧回执不倒退前端确认缓存 |
| 外部ID是否越权 | 真实身份下的owner/id过滤与跨调查关联拒绝 |
| 草稿是否被刷新覆盖 | 原基线/编辑代次/显式确认与真实浏览器时序 |
| 测试是否独立 | 源/求值引用、编译项、解析包、publish与bundle实际检查 |
| 变更是否可维护 | 同一关联修订贯穿需求、领域、合同、迁移、React与回归，不靠新增框架掩盖 |

本次重构不新增业务模块，也不改既有迁移或业务实现。源码边界与测试职责的改进不等于所有生产账户/会话/回执治理能力已实现。继续区分VERIFIED、PARTIAL、BLOCKED和NOT_RUN。

**18-A：** 如果所有测试都通过，却把Mvc.Testing加到API项目里，是否验收通过？参考答案：不能；测试依赖进入生产图违背责任边界，需要检查实际解析与产物。

**18-B：** 旧E10为何不是新DoD？参考答案：所有者明确改变了仓库范围；保留历史链接与事实，当前只验应用工程，不能改写历史编号含义。

**18-C：** 下一次规则变更应先做什么？参考答案：明确业务约束和兼容影响，决定触及的领域、合同、数据、UI和测试；不要先引入新基础设施或拆服务。
