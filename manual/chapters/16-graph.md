# 第 16 章 React Flow：业务关系与本地布局

证据图很容易让开发者把 Node 和 Edge 当成业务模型。控件需要坐标、选中态、缩放和连接手势，业务则需要已调查证据、稳定关系身份和受约束的修订。EchoCase 通过明确映射让两套模型合作，避免拖一次节点就制造一个数据库版本。

## 16.1 控件模型服务于交互

{{figure graph-semantics}}

节点来自 session.evidence 中已调查的证据，Id 沿用证据标识；边来自 session.links，Id 沿用关系 Guid。这样，React Flow 的选中对象能稳定指向已有业务关系。节点坐标、缩放和本地选中态则没有出现在 SessionView 中。

{{code graph-position}}

收到新 session.version 时，Effect 重新映射节点，先按 Id 保留旧位置，新增节点才使用网格默认位置。普通服务器刷新因此不会让用户刚整理的节点全部跳回初始坐标。节点被卸载后位置不再保留，跨页面共享布局也没有实现。

受控节点通过 onNodesChange 和 applyNodeChanges 更新本地数组，控件不直接写数据库。[React Flow 交互模型](https://reactflow.dev/learn/concepts/adding-interactivity)

## 16.2 技术方向与业务方向分开

React Flow 的 Connection 有 source 和 target，表示手势从哪个 Handle 开始。业务关系却是无向的：门禁与领用册之间的矛盾，不因为拖动方向不同就变成另一条事实。根会规范端点次序，数据库唯一键阻止重复。

{{code graph-edges}}

边用关系类型决定文字和颜色，没有添加方向箭头。选中状态只加粗线宽，不改变 Kind。图例和文字都保留类型信息，避免只凭颜色判断。表单式起终点选择与建联按钮提供另一条操作路径，减少对拖拽手势的依赖。

{{figure ui-graph}}

真实图中的关系列表与画布共享服务器快照。画布适合看整体联系，列表适合读解释与执行精确操作。图形不是唯一可访问入口；但当前实现也没有宣称完成所有键盘和辅助技术场景，复杂画布仍需持续验证。

## 16.3 修订编辑器冻结打开时版本

{{code link-baseline}}

打开编辑时，LinkEditor 把 kind、rationale 和当前调查版本放入本地 draft。之后如果父组件收到新版本，draft.version 不自动变化，conflict 会阻止直接保存。否则后台刷新可能悄悄把用户在旧事实下输入的解释改成新版本命令，与笔记章节讨论的静默 rebase 问题相同。

前端用 Array.from(trimmedText).length 统计标量值，与领域 EnumerateRunes 的业务单位对应。类型和值都没有变化时不允许保存，解释不足二十或超过五百也会禁用。服务端仍执行同样业务规则，因为 UI 不能保证所有调用都经过该控件。

## 16.4 等待实际完成，再关闭表单

{{code link-save}}

onSave 返回 Promise，内部是 Workspace 的 mutateAsync。成功路径还会等待 Query 的 onSettled 失效刷新，之后才 setDraft(null)。异常被捕获后保留本地解释，由 Workspace 展示协议错误。错误处理因此保护的是用户劳动，而不仅是控制台没有未处理 Promise。

版本变化时，当前编辑器要求用户保留或复制解释、取消后核对当前关联，再打开修订。它没有笔记那样的三方比较和“确认当前版本”按钮。两个编辑器共享保护基线的原则，具体交互仍按当前复杂度选择，不能在教材中替它补写尚未存在的功能。

{{figure ui-revision}}

真实修订结果中，原有两端保持，关系变成 Contradicts，图边的标签与颜色随确认快照变化，列表出现解释。修订没有创建替代 Guid，也没有把拖拽布局写回服务器。身份、类型、解释和位置分别拥有稳定含义。

## 16.5 窄屏与规模改变设计条件

{{figure ui-mobile}}

窄屏工具栏换行，画布仍能缩放和拖动。这解决的是当前六节点案件的可用性，不能证明大规模图布局、自动聚类或多人布局同步。若未来关系数量大幅增长，默认网格、完整列表和一次加载全部图都需要重新评估。

选择图形库提供的是交互基础，领域约束仍由应用拥有。把边从画布拖出来，不代表业务关系已经成立；只有命令通过规则、版本、幂等和事务，新的确认快照才有权进入图。这个回路与普通表单完全相同，只是呈现方式不同。

## 16.6 派生边与局部节点采用不同更新方式

edges 每次从 session.links 派生，关系类型变更后自然得到新标签与颜色；nodes 需要保留用户拖动坐标，不能每次直接抛弃旧数组。因此一个是确认业务事实的投影，一个是带本地记忆的呈现模型。两者采用不同实现，是因为状态所有者不同。

若把 edges 也长期复制到另一份独立 state，却忘记在服务器修订后更新，就会出现列表已显示矛盾、画布仍显示印证的分叉。若把 nodes 完全从服务器快照重建，又会让普通刷新重置布局。正确的“单一来源”不是全页面只允许一个 state，而是每项事实都有明确的权威来源。

选中关系也只是本地引用。当删除请求失败，服务器关系仍存在，界面下一次确认仍应以服务器为准；本地 selected 清除不代表业务删除成功。用户交互状态可以先变化，但不能因此把数据库事实一并改写。

## 16.7 图形反馈要连接业务语言

绿色和橙色只是一种视觉编码，文字“相互印证”“存在矛盾”才把控件值接回业务。解释位于关系列表，帮助用户理解为什么改变类型。图形越直观，越容易让人把“已经画出来”理解成“已经保存”，所以 pending、禁用和确认刷新同样重要。

当前图谱选择有限节点、简单默认布局和表单备用入口，适合教学案件。自动布局、路径分析或关系置信度都可以成为未来需求，却应从具体用户问题出发。增加动画和算法不能替代现有关联身份与保存语义。
