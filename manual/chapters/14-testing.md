# 第 14 章 单元、集成、架构与端到端测试 {#ch14}

## 测试分层是为了解释失败

领域测试快速回答状态机和不变量是否正确；集成测试回答 EF 映射、数据库约束、身份与 HTTP 组合是否正确；浏览器测试回答 Cookie、表单、缓存、DOM 和真实网络组合是否正确。一个巨大的 E2E 套件可以发现问题，却未必能快速定位；只做单元测试则会漏掉本项目已经遇到的两个 ORM 与缓存缺陷。

| 层级 | 真实组件 | 被替代部分 | 主要证据 |
|---|---|---|---|
| 领域 NUnit | 领域对象与规则 | 时间使用固定值 | 不变量、状态转换、失败不变性 |
| 架构 NUnit | 编译后的程序集 | 无数据库 | 向内依赖 |
| API 集成 | ASP.NET 管道、Identity、EF、PostgreSQL | TestServer HTTP 宿主 | 事务、权限、并发、幂等 |
| Playwright | Edge、HTTP、API、数据库 | 个别显式注入响应 | 完整流程、回滚、双窗口、移动端 |
| SQL 实验 | PostgreSQL 与连接 | 业务数据为合成 | 隔离与计划机制 |

## 测试数据隔离与清理

每次集成运行创建随机命名的 echocase_test_ 数据库，迁移到最终模式，建立两个账户，在结束时只删除该精确数据库。测试方法各自开始新的调查，不依赖前一方法留下的状态。共享登录客户端减少速率限制干扰，但不共享被断言的调查对象。

清理代码必须像实现一样被审查。数据库名称来自受控前缀与随机十六进制，使用引号保护；不会接受任意用户输入作为 DROP 目标。外部实验只停止本项目自己的容器，不重启整个 WSL，也不清空开发卷。失败也进入 finally 恢复，防止把故障留给用户。

## 并发测试需要独立上下文

两个任务共享一个 DbContext 并不是真实并发测试，因为 DbContext 不支持这样的线程使用；它可能先抛框架错误，掩盖业务竞争。当前 API 并发请求各有作用域，EF 双写测试明确创建两个上下文，SQL 隔离实验创建两个连接。

并发断言应检查整体结果：一方成功、一方冲突，数据库只保留一次更新，失败者没有回执。只断言“没有异常”或“最终版本大于 1”，无法识别双重提交。对同键重试，则应要求双方看到同一次操作结果，并确认审计只写一次。

## 浏览器测试验证用户可见结果

完整工作流从注册开始，调查六条证据，建立两条关联，保存笔记，刷新验证，进入复核，提交并刷新归档结果。测试使用角色和标签定位，不依赖 CSS 类序号来操作按钮；截图则记录关键稳定状态，作为教材插图与视觉审查材料。

回滚测试在浏览器层明确注入 503，再直接读取 API 核对服务器事实。双窗口冲突使用真实竞争，不伪造错误响应。移动端验证特定视口无横向溢出。测试没有把模拟响应标成真实数据库故障，真实停库由独立可靠性实验负责。

## 历史失败比“最后全绿”更有解释力

首次迁移缺少工具引用，导致集成库没有表；后续测试发现关联主键状态推断错误、审计唯一约束冲突映射错误；首轮浏览器发现清空 QueryCache 后登录观察器失联；可靠性实验发现 EF 包装异常没有映射为 503。这些失败保留了原始结果与修复后的证据。

它们支持的是“这些具体测试发现并阻止了这些缺陷”，而不是“测试可以证明没有缺陷”。当前没有统计代码覆盖率，没有运行长期压力、全面渗透、所有浏览器兼容或无障碍认证。验收报告应保留这些限制。

## 实验 E14：测试门禁是否真的会失败

对 QA 工具创建临时损坏副本：删除证据文件、改坏摘要、把预期通过状态改成不存在的枚举、引入外向依赖、让性能样本超过门槛。运行同一个检查入口，必须返回非零。再验证正常副本通过。这个自测保护的是验收工具本身，避免“发现错误但退出 0”的假门禁。

一个门禁测试只检查自己输出含 FAIL 仍然不足，因为 CI 以进程退出码决定后续步骤。需要捕获真实 returncode，并在自测中断言它。故意损坏的文件不提交进正常源目录，只把损坏类型与结果写入证据。

## 练习与参考答案

**14-A：** 哪个测试能发现登录页缓存问题？参考答案：浏览器或针对 QueryObserver 生命周期的前端集成测试。后端登录 API 测试无法观察 React 订阅关系。

**14-B：** 为什么不把所有测试都改用内存数据库？参考答案：它不能复现 PostgreSQL 外键、锁、隔离、SQL 状态与查询计划，也可能掩盖 EF 翻译差异。领域测试本来就不需要数据库；持久化测试应使用真实目标引擎。

**14-C：** 测试运行失败后，什么证据能区分代码缺陷与环境故障？参考答案：保存退出码、测试名称、错误形状、数据库版本、迁移状态和重现条件；修复环境后重新运行相关检查。不要直接把所有失败标记为 flaky。
