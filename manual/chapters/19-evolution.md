# 第 19 章 把“修订关联”作为一次完整需求演进

真实需求变化通常不会只落在一个文件。允许修订关系类型并补充解释，看似很小，却会影响身份、规则、数据库、回执、协议和前端编辑。维护能力来自识别这些必要影响，并复用已有保证，而不是通过一次变化引入一整套新框架。

## 19.1 先确定什么保持，什么改变

原系统已经能建立、删除关系。新需求要求修改同一关系的判断，因此 Id 与端点保持；Kind、Rationale 和 RevisedAt 变化；根版本前进一次。Active 才能执行，二十至五百个标量值的解释是必需内容，相同类型和解释应拒绝。

{{figure evolution}}

这个定义排除了“删除再创建”和“直接改子表”两种看似快捷的实现。前者破坏身份，后者绕过根版本和共同事务。需求越清楚，需要触及的边界反而越少：新增一个根行为和对应端点，沿共享 Write 进入原有幂等、审计和并发路径。

## 19.2 领域新增行为，应用复用协议

ReviseLink 的校验都在赋值之前，子对象内部 Revise 只接收已经通过规则的值。Service 做精确枚举转换，将 linkId 和正文放进指纹。Store 无需再为这项操作复制一套锁、回执和事务逻辑，只记录新的 operation 名。

这种复用有具体前提：新行为仍然只改变一个调查聚合，仍是本地数据库副作用。若需求变为“修订后必须发送可靠外部通知”，共享 Write 还不够，不能为了减少代码而忽视副作用边界。抽象只能复用相同承诺，不能强行吞下不同承诺。

## 19.3 持久化兼容贯穿三条路径

新列可空，旧行不补虚构说明；新行为写成对值，数据库约束拒绝半对；旧 LinkView JSON 缺字段时使用默认 null。这里同时保护已有表行、新写入和旧回执。迁移文件成功只是其中一项事实。

真实跟踪观察中，旧关系的 Rationale 仍为 null；修订后子对象只有 Kind、Rationale、RevisedAt 变脏，根只有 Version、UpdatedAt 变脏。成功保存后版本从 4 到 5；旧版本尝试的子修改随事务失败回滚。这个结果让“新增行为没有绕开原保护”成为可以解释的结论。

## 19.4 新端点不改变旧端点的全部接受范围

PUT 使用已有关系 Id 和新请求类型，不接收新端点。精确枚举名称保证新合同清晰，旧 POST 的数值字符串兼容行为则没有顺便重写。需求演进中，统一与兼容经常冲突；若想收紧旧行为，应作为单独合同变化评估，而不是夹在“新增功能”里无声发生。

返回仍为完整 SessionView，ETag 使用新根版本，幂等指纹包含操作与 linkId。两个目标不同的修订不会被误认为同一请求，复用旧键表达新解释会得到 409，旧版本的新修订得到 412。它们继承的是原协议，而不是客户端碰巧没有重复点击。

## 19.5 前端拆分围绕变化原因

LinkEditor 拥有打开时版本和字段草稿；EvidenceGraph 负责从确认关系映射边；useInvestigation 负责请求和缓存；Workspace 负责接线与统一错误。每个模块都有一个可以用自然语言说清的状态所有者。

保存失败时解释保留，成功并完成必要刷新后表单关闭。后台新版本使旧编辑变成冲突，不能自动换上新版本再发。图布局不写入数据库，所以增加解释不会额外改变本地节点的业务含义。

这类拆分修复了大组件中容易隐藏的耦合：一个成功回调原本可能同时清草稿、写缓存、关表单和换页签。现在每项更新依据自己的前提发生。文件变短只是副产品，真正收益是可以分别推理。

## 19.6 评审应从用户承诺逆向阅读

{{figure review-model}}

从“同一关系被修订”回到 Guid 和端点；从“不会丢别人的修改”回到根版本与真实 UPDATE；从“网络失败可以恢复”回到指纹和历史回执；从“等待时可继续写”回到 revision 和确认条件。这种逆向追踪能发现某层遗漏，而不是只看每个文件是否符合样式。

必要验证也沿这些承诺展开：纯领域断言身份和计数单位，真实数据库断言迁移与回滚，浏览器断言编辑器和确认状态。无需为每个新增文件创造一个镜像测试，也无需把一次小需求升级成全面 QA 平台。

一次良好演进结束后，系统应更容易解释。新规则有唯一入口，旧数据意义没有被改写，已有协议继续承担相同职责，用户在错误和并发下仍能做出清楚决定。这样的维护质量可以从具体行为看出来，无需用复杂度装饰它。

## 19.7 变更影响图为什么比文件清单有用

文件清单告诉人哪里动过，却不解释为什么必须一起改变。关联修订的影响图从“身份保持”连到领域方法和 UI key，从“新解释”连到列与旧 JSON，从“旧窗口保护”连到根版本和编辑基线，从“结果未知”连到同一回执协议。每条边都对应一项承诺。

若某个新增文件无法连到承诺，可能是无必要复杂度；若某个承诺没有任何落点，可能是遗漏。这样的评审比逐文件看语法更容易发现跨层空隙，也能让不同专长的人讨论同一件事。数据库工程师和前端工程师不需要懂对方每个 API，仍能围绕“失败后解释不能丢”建立共同判断。

## 19.8 什么时候应该停止重构

当规则入口明确、已有协议能够复用、失败反例得到保护，继续把所有相似代码抽成通用框架未必增加价值。NotesEditor 与 LinkEditor 都有基线，却有不同确认交互；过早强行统一，可能把两种清晰行为塞进充满开关的通用编辑器。

停止的依据不是“代码已经最短”，而是当前变化可以清楚推理，剩余差异有实际理由，未来改变条件被记录。维护性包含克制：保留可解释的简单实现，并知道什么新需求会让它不再足够。
