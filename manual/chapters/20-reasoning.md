# 第 20 章 设计推理题与解析

本章的问题不要求先准备环境。每题先给出事实，请读者预测结果并说明理由，再对照解析。判断依据是前面各章建立的对象、快照、事务与意图模型；若需要深究实现，可从所列符号进入源码。

## 20.1 成功响应能否清掉新输入

事实：服务器笔记为空、版本 1。用户输入 A 后保存，操作带 revision 1。等待期间用户又输入 B，当前文本变为 A+B、revision 2。服务器成功返回 A、版本 2。有人建议“既然成功，就把 dirty 设为 false”。这是否正确？

解析：不正确。成功确认的是发送出去的 A/r1，不包含 B。正确状态是确认缓存进入 v2/A，草稿基线进入 v2/A，当前文本保持 A+B，dirty 为 true。若响应来自更旧回执且 current 已更高，还不能借它推进当前草稿确认。关键符号是 useNotesDraft 的 draftRevision 比较与旧版本提前返回。

把判断改成“响应 notes 与当前 text 不同就保留”仍不完整。用户可能删回相同文本，但编辑代次与意图已经变化；字符串相等不能表达全部时间关系。代次提供的是因果信息。

## 20.2 幂等重试为什么不能换新版本

事实：K 在版本 4 上成功，生成版本 5，但客户端断线。另一窗口又生成版本 6。客户端恢复后把原 body、原 K 与最新 If-Match 6 一起重发，认为这样更容易通过。会发生什么？

解析：版本进入指纹，原 K 对应的是版本 4 的请求，换成 6 后应得到 409。正确重试保留 K、4 和原 body，恢复版本 5 的历史成功；确认缓存保持已经取得的 6。若用户看过版本 6 后确实想再次保存，应建立新键的新意图，仍可能遇到后续竞争。

这题区分资源前提与操作身份。版本不是为了“找到能通过的数字”，而是表明用户作决定时看过什么。

## 20.3 只给子表加版本能否保持原语义

事实：为了减少冲突，开发者删掉根版本推进，只在 EvidenceLink 上增加独立版本。笔记修改和关系修订于是可以同时成功。是否可以宣布这是无风险优化？

解析：不可以。它改变了调查的决定边界。原来任何成员变化都要求旧窗口核对，现在关系判断可能在未见新笔记的情况下成立。若业务证明两类决定独立，可以设计更细版本；还需重新考虑复核状态、发现条件、审计版本与读模型。性能收益不能代替语义证明。

若只是对子表加版本，同时保留根版本，系统会更保守并增加复杂度，却未必获得更高并发。每个令牌都需要明确保护的事实。

## 20.4 DetectChanges 前 Unchanged 是否说明保存失效

事实：调用 ReviseLink 后，调试看到两个条目仍是 Unchanged，但 CLR 中 Version 已加一、Kind 已改变。有人准备调用 Update(root) 强行标记整图。该如何判断？

解析：先确定是否已经运行变更检测。默认快照跟踪不保证每次普通赋值后立即改变条目状态；真实观察中 DetectChanges 后只把相关属性标脏。强行 Update 整图可能掩盖真正问题，也可能把无需修改的字段一并发送。应比较当前值、原始值、生成策略与 SQL，再判断是否存在漏存。

若新子成员被标成 Modified 而应为 Added，则需要检查键生成配置。并发异常还可能由更新不存在的行造成，不能只凭异常名认定其他用户竞争。

## 20.5 复合索引消除了所有排序吗

事实：复合索引让根查询直接取五十行，计划外层仍有 Incremental Sort。有人认为索引没有生效，因为还能看到 Sort。如何解释？

解析：根选择的排序与外层为连接物化安排的完整排序不是同一节点。代表计划已显示根由有序 Index Scan 输出五十行，外层仍按根 Id、发现键等整理连接行。应沿树定位工作，结合 rows 和 loops，而不是搜索某个单词判成败。

中位数从 4.037 ms 到 0.929 ms 只说明给定暖缓存样本中的数据库执行变化，不能直接变成 API P95 承诺。测量单位与适用范围同样属于答案。

## 20.6 新解释列能否全部补成迁移时间

事实：旧关系没有修订解释和时间。有人为减少 null，把解释设为“历史关联”，时间设为迁移执行时刻。新界面因此不必处理空值。这合理吗？

解析：不合理。它把技术迁移伪装成业务修订。旧事实应继续用成对 null 表达，新修订写真实解释与业务时间，界面明确展示有无解释。还要保证旧回执 JSON 可恢复，而不是只让新表查询通过。

数据清洁不等于所有列非空。缺失事实有明确意义时，诚实保留缺失比制造完整表象更重要。

## 20.7 把图坐标放进 Version 会怎样

事实：为了跨窗口共享布局，开发者打算每次拖动都更新 Investigation.Version。会带来什么影响，是否一定不应该做？

解析：拖动会与笔记、关系、复核竞争同一版本，后台布局同步可能不断触发草稿冲突。高频手势还需要节流、提交和失败恢复。若共享布局确有业务价值，可以设计独立布局资源或明确纳入调查协议；不能只把局部 position 序列化后就忽略一致性成本。

答案不是禁止持久化坐标，而是要求先决定布局属于共享业务事实还是个人呈现。不同所有权需要不同版本和权限边界。

## 20.8 发送通知能否放进 SavingChanges

事实：修订成功后需要发邮件。开发者在保存前事件中发送，随后数据库根 UPDATE 发生冲突并回滚。用户收到邮件说修订成功。应怎样理解这个失败？

解析：外部邮件不在 PostgreSQL 事务里，不能随回滚撤回。当前本地事务协议已超出适用边界。应考虑在事务中持久化待交付事实，提交后由独立交付过程发送并处理重试、去重与状态；仅把调用移到另一个类，不会建立可靠性。

这些题可以继续延展，但应保持同一种推理习惯：先标出事实的时间和所有者，再判断哪个操作有权改变它。源码可以帮助检查机制，理解则来自因果关系。
