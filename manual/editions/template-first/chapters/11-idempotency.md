# 第 11 章 幂等回执与结果未知

客户端没有收到成功，不代表服务器没有成功。事务可能已经提交，响应却在网络中丢失；也可能 HTTP 200 已经到达，但正文无法解析。此时若客户端生成新键、换成最新版本并再次保存，就把“确认原操作”变成了“再做一次新操作”。

## 11.1 幂等保护哪一段副作用

EchoCase 的命令只改变本地 PostgreSQL 里的业务、审计和回执，没有发送邮件或调用外部支付。幂等协议因此能把这些副作用放进同一个事务：要么全部提交，要么都不成立。回执中的 Response 是成功时投影的 SessionView。先提交业务再补回执，会留下已成功却无法重放的缺口；先提交回执，则可能为失败业务制造虚假的成功证明。

{{code model-receipt}}

Receipts 以 (OwnerId, Key) 唯一，审计以 (InvestigationId, Version) 唯一。前者识别用户意图，后者约束调查版本事实。它们不能互相替代：两个不同键仍会竞争同一版本；同一个键的重试则不应再次推进版本。

“幂等”在这里不表示网络只发送一次。网络可以多次传送相同请求，服务器在既定范围内确认同一提交。若未来加入外部副作用，本地回执无法让远程系统自动参与回滚，需要新的交付设计。把当前保证称作任意系统的 exactly-once，会越过实现边界。

## 11.2 同键锁让回执检查串行发生

{{figure receipt-lock}}

Store 在事务内对 owner 与 key 拼接后的名字哈希加事务级 advisory lock。第一次请求获锁后加载、判断、修改并提交；同键重试等待。获锁后再读回执，Read Committed 的新语句可以看见先前提交结果，便不再执行领域回调。[事务级 advisory lock](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS)

事务级锁在提交或回滚时释放，不依赖连接池恰好关掉连接。64 位哈希理论上可能碰撞，两个不相关键因此多等待一会儿；真实回执仍按 owner/key 精确查询和指纹比较，所以碰撞不会把一个用户的响应当成另一个键的结果。锁解决排队，精确键解决身份。

该锁不是调查级锁。不同键可以同时推进到同一根的版本仲裁，前章真实竞争正是这种情况。若误以为 advisory lock 已经序列化所有调查修改，就可能删掉根版本条件，从而破坏另一条竞争路径。

## 11.3 为什么先检查资源，再读取回执

写路径先按 id 与 owner 加载调查，再查 owner/key 回执。这样，即使调用者持有一个可猜测的键，也不能借回执绕过对目标调查的可见性判断。回执属于意图记录，不是免授权凭证。

这里指带 SessionId 的既有调查修改。Start 尚无既有目标，Store 不进入目标加载分支，而按 owner/key 确认创建意图。当前没有生产所有权转移 API，不能把笔记修改的夹具结论推广成任意未来权限变化下的统一保证。

找到回执后，指纹不同返回 409，相同则直接恢复历史 SessionView；版本前置比较发生在没有回执的路径。这一顺序允许第一次已成功、现在资源版本更高的原样重试仍被确认。若把版本比较放在重放之前，原请求使用的旧版本会使每次重试都被拒绝，回执就失去意义。重放分支不执行 apply、不增加审计，读取事务离开作用域时释放锁，不再为确认过去制造新业务变化。

同时，重试不能只保留键却更换 body 或 version，因为这些内容进入指纹。一个键只能表达一个确定意图。客户端若希望采纳最新服务器状态重新保存，需要让用户确认并生成新键，那属于下一次业务决定。

## 11.4 历史结果不是最新资源

设命令 K 在版本 4 上成功，产生版本 5。随后另一个命令产生版本 6。K 的重试应返回版本 5 的历史成功结果，不应伪造为版本 6，因为版本 6 不属于 K 的决定。

前端仍需要知道两件事：K 确实成功了，当前资源却已经更晚。Query 缓存的单调版本规则保留 6，草稿确认逻辑则拒绝用旧回执清掉仍需用户判断的输入。一个 HTTP 200 因此可以确认历史操作，却不能授权界面回到旧状态。

这种区分在业务系统中很普遍。订单创建回执确认订单曾建立，不代表它仍未取消；审批回执确认某步曾通过，不代表整个流程仍停在那一步。回执具有操作时间语义，资源查询具有读取时间语义。

## 11.5 客户端怎样保留不确定性

{{figure uncertain}}

{{code client-fetch}}

生成客户端通过注入 transport 调用 fetch，apiCall 在外层捕获失败；若不是主动 AbortSignal 取消，客户端生成 status 0 的 ApiError。取消查询是有意停止，不应该被展示成写入结果未知；真实断线则不能断言事务失败。这个细分避免每次查询取消都触发恢复流程。

{{code client-body}}

HTTP 成功正文由 NSwag 生成处理器读取和解析，apiCall 将其解析失败纳入结果未知分类。它不验证所有合法 JSON 的字段形状；空成功正文可能被生成器接受为 null，不能据此承诺完整运行时 schema 验证。真实测试在服务器提交后截断 JSON，浏览器无法构造可信 Session。错误文字保留原操作重试的含义，而不是把 200 当作足够的确认。

{{code query-uncertain}}

blocked 在 pending 或 uncertain 时阻止发出新的不同写入。笔记输入仍能继续，因为输入是本地草稿，不立即产生服务器副作用。工作台的“重试同一次操作”使用 mutation.variables 原样再次调用，因此 kind、目标参数、body、version、key 和草稿代次均保持不变；executeOperation 选择生成 SDK 方法，apiCall 继续携带原协议上下文。

{{figure ui-unreadable}}

截图记录的是正文不可读之后，经原意图重试恢复确认的真实界面，而非错误刚发生的瞬间。它与受控网络反例一起说明：恢复不是把输入重新包装成任意新请求，而是从持久回执取得第一次操作的确定结果。

## 11.6 当前保证的边界

回执没有自动过期或清理策略，幂等保护因此依赖数据持续保留。它保留完整 SessionView，随规模增长会增加存储成本；新 DTO 演进也必须考虑旧回执。清理时限若未来引入，就会改变“多久以内可安全重试”的公开合同，需要产品和客户端一起理解。

当前状态 0 分支不覆盖所有可能的提交确认丢失形式，也没有把未知操作持久化到浏览器以供重启恢复。刷新或关闭页面可能失去本地变量。一般 5xx 也没有统一纳入恢复队列。这些限制不会否定现有保护，却决定了不能宣传成通用离线写入框架。

一个好的幂等设计，既要知道如何重放，也要知道哪些事实不能从重放推导。它确认一次已记录决定，不替用户制造下一次决定。

## 11.7 三种重复要分开处理

| 情形 | 请求身份 | 正确含义 |
|---|---|---|
| 网络重传原请求 | 同 owner、同 key、同指纹 | 恢复原成功，不再次应用行为 |
| 用户再次作决定 | 新 key，可有相同正文 | 按当前前提执行新的命令 |
| 错误复用旧键 | 同 key，不同版本或正文 | 409，拒绝把历史身份改成新意图 |

相同正文并不足以识别重复。用户可能在新事实下再次保存相同文字；也可能只是某次响应没有收到。若服务器只按 body 去重，会把正常新决定与恢复混淆；若只按版本去重，不同操作也可能共享同一前提。当前协议把这些维度分别保存，客户端明确选择属于哪种情况。

没有回执的失败请求不构成已成功记录。领域校验在持久保存前抛错时，不会留下成功 Response；事务失败也不保留半条回执。客户端仍应保持意图使用清晰，不能把“未占用某键”当作随意变换同键正文的恢复协议。
