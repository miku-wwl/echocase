# 第 8 章 数据模型演进与时间精度

增加“关系解释”看似只需要两列：Rationale 和 RevisedAt。真正困难在于旧数据没有这两个事实，旧成功回执中也没有对应字段，而新界面却必须能区分“从未修订”和“已经修订”。安全演进首先需要定义缺失值的含义，再讨论迁移语法。

## 8.1 null 可以表达真实历史

旧关系只包含端点和类型，没有说明何时以及为何修订。迁移若给所有旧行填“历史记录”并写入迁移时间，就制造了没有发生过的业务行为。EchoCase 选择两列都可空：二者均为 null 表示没有可记录的修订解释；新修订则同时写入解释与业务时间。

这是加法式演进，原 Id、端点和 Kind 不变。数据库 CHECK 进一步要求两列要么同时为空，要么同时非空且解释长度在二十至五百之间。只加一个 nullable 字符串而不建立配对规则，会允许“有解释却不知道何时修订”等没有明确定义的状态进入持久层。

可空并不是宽松到任何内容都合法。领域的 Trim 和标量值计数仍处理新业务输入；数据库的 varchar 与 char_length 保护持久边界。当前规则使用 Unicode 标量值，与 PostgreSQL UTF-8 数据库中字符计数相配。若业务改成“用户感知字数”，组合字符和表情簇就需要重新定义，不能只改界面上的提示文字。

## 8.2 约束之间怎样合作

关系 Id 是主键；(InvestigationId, SourceId, TargetId) 唯一索引防止重复无向对；两个复合外键把端点连接到同一调查的 Discoveries；CHECK 拒绝自连、非法 Kind 和非规范顺序。不同约束分别保护身份、唯一性、成员归属和局部值域。

它们没有完整实现 Active 才能修改，也没有证明结论理由充分。将所有领域规则都复制到数据库触发器并非当前选择。日常写入走聚合，数据库兜住适合关系模型的事实。评审时应逐条判断保证来自哪里，不能用“有数据库约束”笼统覆盖所有规则。

唯一索引还具有竞争语义。两个事务即使都在各自快照中看不到冲突，最终也不能同时保存同一唯一键。第十章会看到，(InvestigationId, Version) 审计唯一索引甚至可能在根 UPDATE 之前发现竞争。因此约束不只是静态 schema 文本，也是运行时仲裁的一部分。

## 8.3 旧回执是另一份持久合同

{{code app-linkview}}

LinkView 的新增参数提供 null 默认值，让旧 JSON 缺少字段时仍能恢复视图。回执保存的是序列化成功响应，不会随着表结构升级自动重新生成。如果只验证新数据库查询能返回两列，却忘记重放旧 JSON，网络重试就可能在升级后失败。

旧回执重放后仍应表达旧操作成功时的事实，而不是给它补成当前调查。否则幂等键不再确认原操作，变成了另一种隐藏查询。返回旧形状兼容恢复的目的，是维持这份历史语义；最新资源由正常 Get 再取得，前端负责不让旧回执倒退当前确认缓存。

这也是“向后兼容”需要具体对象的原因。表行兼容、HTTP 请求兼容、响应消费者兼容和存储 JSON 兼容是四个问题。一个字段可空只回答其中一部分。严谨的改动应沿着所有实际持久表示追踪，而不是只看迁移能否执行。

## 8.4 时间相等为何曾经失败

2026 年 11 月 11 日历史运行中，一次真实保存的即时响应与随后重读，tick 值分别为 `639299746962572167` 和 `639299746962572160`，相差七个 tick，也就是 0.7 微秒。用户界面几乎看不见这个差异，但逐值合同和回执比较能看到。原因是 .NET 的时刻分辨率比 PostgreSQL timestamp 的微秒精度更细。[PostgreSQL 时间类型](https://www.postgresql.org/docs/17/datatype-datetime.html)

{{figure time-precision}}

{{code app-time}}

修复在业务时间进入领域之前截去不足微秒的尾数，而不是等读取时再用模糊容差隐藏差异。这样，即时响应的领域时间、序列化回执和数据库重读有相同可表达精度。实际修复后观察中的两个值都为 `639299753895425590`。

时间精度与时间格式不同。把同一时刻格式化成不同小数位，或者以不同 UTC 偏移显示，未必改变时刻；这里原先的值确实有精度损失。当前实现统一传入 UTC，而不是要求 PostgreSQL 替我们保留原始显示时区。需要保存“用户当时所在时区”时，应增加独立业务字段，不能指望 timestamptz 自动记住所有输入形式。

这项修复不会把历史回执中的高精度时间重新写一遍。旧回执仍是旧操作记录。对未来保证和历史行为应分开描述，避免在兼容处理中改写事实。

## 8.5 Down 能撤销结构，不能恢复丢失的解释

迁移的 Down 会删除约束和两列。若这些列已经保存新解释，删除它们就会丢失业务信息；因此“存在 Down 方法”不等于无损回退能力。本书不把 schema 的逆操作包装成完整的数据恢复承诺。

对于这次加法演进，旧列集中的身份、端点和类型可以保留，新代码理解 null，新输入填入成对新字段。若未来改为重命名、拆列或改变含义，则需要更细的读取兼容与数据转换设计。演进安全取决于语义和数据流，不由 EF 生成文件的长度决定。

## 8.6 CHECK 与 null 的三值逻辑

SQL 表达式可能得到 true、false 或 unknown。一个简单的 char_length(Rationale) 范围条件，在 Rationale 为 null 时不会像普通 C# bool 那样直接得到 false；CHECK 也不能被当作隐式 NOT NULL。当前约束显式组合两种合法情况，避免让半对空值滑过。[PostgreSQL 约束语义](https://www.postgresql.org/docs/17/ddl-constraints.html)

| Rationale | RevisedAt | 当前配对规则 |
|---|---|---|
| null | null | 合法旧状态，未记录修订 |
| 有效解释 | 非空时间 | 合法新修订 |
| null | 非空时间 | 拒绝，缺少解释事实 |
| 有解释 | null | 拒绝，缺少修订时间 |

数据库仍可能接受二十个空格，因为 char_length 计算长度而不自动执行领域 Trim。领域会把它清理后拒绝。这再次说明相近校验的边界不同：数据库保护持久形状，领域保护新行为语义。直接写表不是合法业务 API。

## 8.7 schema 快照不是业务历史

EF 的模型快照描述当前映射，用于后续迁移差异；迁移文件描述结构变化；Audit 描述应用操作；Receipt 描述某次成功结果。这四份材料都可能随时间增长，却不是同一种历史。修改模型快照不能补出旧关系的解释，审计版本也不能替代真实字段迁移。

关联修订的 additive 设计让旧列集继续有意义，新列含义可被准确区分。若以后需要保留每次解释全文，当前只保留最新值和操作审计还不够，需要单独的修订历史模型。现有 Audit 没有完整前后值，也没有防篡改保证，不能在需求未实现时称作完整审计账本。
