# 第 15 章 草稿基线、输入代次与显式冲突

保存按钮最容易作出的错误承诺，是收到任何成功响应就把当前输入标为已保存。服务器只确认发送出去的正文，不知道用户在等待时又输入了什么。EchoCase 用基线和输入代次，把“用户正在写什么”与“某次操作确认了什么”区分开来。

## 15.1 一份草稿需要记录哪些事实

{{code draft-initial}}

text 是当前输入；baseline 是开始编辑时的已确认笔记；version 是这份基线对应的调查版本；revision 是本地编辑代次；dirty 表示用户有待确认的编辑意图；saved 只表达当前可展示的保存确认。它们不是六份重复数据，而是回答六个不同问题。

dirty 使用显式布尔值。用户输入后又把文字删回原样，也可能仍在进行一次编辑会话；后台刷新不应因为字符串碰巧相等就偷偷改变她的基线。若产品希望“恢复原文自动视作未编辑”，可以另行定义，但必须一起考虑后台变化和代次确认，不能只替换成一个字符串比较。

{{code draft-edit}}

每次 edit 增加 revision，清除 saved，并保持 dirty。函数式更新让事件与异步确认排队时仍基于当前草稿前值。资源 Version 与 revision 互不替代：用户可能在服务器版本 4 上编辑十次，也可能一次未输入就收到版本 8。

## 15.2 发出保存时冻结哪一份东西

{{code draft-operation}}

operation 捕获正文、基线版本、随机键和 draftRevision。请求发出后，这个对象不随输入框继续变化。正常保存使用 draft.version；用户显式确认冲突后才使用 current.version。两者都会建立新键，因为那是一次新决定，而原请求重试仍由 mutation.variables 原样保存。

{{figure draft-generation}}

把时间线展开：初始服务器版本 1、笔记为空；用户输入 A，revision 为 1；按保存发出 A/r1；等待期间继续输入 A+B，revision 为 2；服务器确认 A，版本为 2。正确结果是基线更新成 A/v2，输入框保持 A+B，dirty 仍为 true。

| 时刻 | 确认服务器 | 本地输入 | 草稿基线与状态 |
|---|---|---|---|
| 开始 | v1 / 空 | 空 | v1 / clean |
| 第一次输入 | v1 / 空 | A / r1 | v1 / dirty |
| 保存发出 | v1 / 空 | A / r1 | 操作固定 A、v1、r1 |
| 等待中再输入 | 尚未确认 | A+B / r2 | 仍基于 v1，保留新文本 |
| A 保存确认 | v2 / A | A+B / r2 | 基线变 A/v2，仍 dirty |

## 15.3 成功确认必须对应代次

{{code draft-ack}}

当前确认逻辑先检查 operation.kind 为 notes，避免把其他命令成功当成笔记保存；随后，当当前 revision 等于发送时 draftRevision，响应可以确认这份输入：使用服务器规范化的 notes，更新基线与版本，清 dirty，显示 saved。若代次已增长，响应只推进本次操作能够确认的基线，保留当前 text 和 dirty。于是用户能在保存期间继续工作，而无需锁死输入框。

此外，每个成功键只确认一次，acknowledged ref 防止后续渲染重复处理同一个操作。旧回执若 result.version 低于 current.version，会提前返回，不把过去成功当成当前内容。这里不需要让 ref 驱动渲染，它只是记录一项处理身份；可见状态仍在 state 中。

{{figure ui-inflight}}

真实运行中，服务器笔记为“先提交的观察”，输入框仍有“先提交的观察；等待时继续记录的新线索”。截图中“有未保存的修改”与可再次保存的按钮共同说明，新输入没有被晚到响应清掉。一个泛泛的成功 toast 无法表达这项区别。

## 15.4 后台刷新不能静默替换基线

{{code draft-refresh}}

干净草稿可以跟随 current.notes 与 current.version，因为用户没有尚未处理的编辑。脏草稿则保持 text、baseline 和 version，让后台新事实只进入确认缓存。否则用户本来基于版本 1 写出的判断，会在不知情时被包装成基于版本 2 的保存，绕过冲突确认。

conflict 的条件是 dirty 且 current.version 大于 draft.version。它可能由另一窗口修改笔记触发，也可能由同一调查的其他成员改变触发。由于版本属于整个聚合，界面保守要求核对。当前实现没有细分“只有关系改变所以笔记可自动合并”，这与后端根版本策略一致。

{{figure ui-dirty}}

真实场景中，基线笔记为空且版本为 1；本地草稿是“本窗口的待核实推断”；另一窗口已经保存“另一窗口已经核实的事实”，当前为版本 2。比较区将三份内容并排解释，用户才知道发生了什么。只显示“有冲突，请刷新”，会让她无法判断刷新是否会删除输入。

## 15.5 两种确认是两种决定

“采用服务器内容”丢弃本地草稿，按当前快照重置 text、baseline、version，并增加本地代次，防止旧操作确认混入。它不需要发新写入，因为只是本地选择。

“确认保留草稿并基于当前版本保存”则建立新的 Operation，使用当前服务器版本和新键。它不是重试旧请求，而是用户看过差异之后作出的新决定。如果确认之后又有其他请求提交，仍可能再次得到 412；界面确认不能冻结世界。

当前比较没有实现自动文本合并，也没有识别段落级冲突。对于短笔记，显式选择更容易解释；若扩成长文协作，需要新的合并模型与用户体验，而不是把 baseline/version 逻辑悄悄移除。

## 15.6 输入可继续，不代表所有操作都能继续

未知写入期间可以继续编辑笔记，但 blocked 阻止新的保存和其他业务写入，直到原操作有明确结论。这样既保护工作连续性，也避免在未知结果之上叠加更多难以辨认的决定。LinkEditor 当前在 disabled 时会禁用自己的字段，与笔记策略并不完全相同，不能把笔记行为推广成全应用所有表单的保证。

草稿保存在工作台挂载生命周期中，关闭页面或切换调查会失去未保存内容。这是当前实现的实际边界。增加持久草稿时，还要决定用户隔离、版本过期、隐私与恢复提示；把一个字符串写进 localStorage 并不能自动解决这些问题。

从一次晚到响应看出去，可以发现前端一致性并非后端事务的附属。后端保护持久事实，前端保护尚未持久的用户意图。两者都正确，一次保存才值得用户信任。

## 15.7 把确认逻辑读成状态转移表

| 到达事件 | 当前前提 | 草稿应怎样变化 |
|---|---|---|
| 新服务器快照 | clean | 文本与基线跟随确认值 |
| 新服务器快照 | dirty | 保留文本与旧基线，比较版本 |
| 本次保存成功 | 同输入代次、结果不旧 | 接纳规范文本并清 dirty |
| 本次保存成功 | 已有后续输入 | 只推进已确认基线，保留当前文本 |
| 历史回执成功 | 结果低于当前版本 | 不用它清除草稿 |
| 用户采用服务器 | 明确放弃本地意图 | 重置到当前快照，推进代次 |
| 用户确认保留 | 已看过当前差异 | 新键、新前提，形成新操作 |

表格不是另一套实现，而是把代码中的条件翻译成可审阅语义。某次修改如果让一个分支无法对应明确用户含义，就说明状态模型可能重新混淆了。尤其不能把 success 作为所有分支的共同清理入口。

## 15.8 自己保存成功，却又出现冲突

设本窗口保存 A/v4，服务器产生 v5；响应回来之前，另一窗口把调查推进到 v6；本窗口的确认刷新先取得 v6。随后原操作完成，result 仍为 v5。当前实现拒绝用这个旧成功清理草稿，因此即使原 A 确实保存过，用户仍需核对现在的事实。

这不是“服务器否认自己的成功”，而是两种结论同时成立：原操作已经提交，现在资源已经超越它。若界面只容纳一个 saved 布尔值，就很难表达这种关系。current、result、baseline 和 operation 各自保留来源，才能作出保守且可解释的选择。

用户继续输入也可能与保存规范化交错，例如服务器 Trim 去掉前后空格。只有同代次确认才将输入框替换为规范结果；有后续输入时，保留当前文本更重要。基线更新说明原操作已确认，不表示未经发送的新文本已被服务器规范化。

## 15.9 为什么不在 Effect 中自动“修复”冲突

自动把 draft.version 改成 current.version，表面上能解除冲突提示，却抹掉了用户尚未看过的新前提。自动把 draft.text 改成 current.notes，则直接放弃本地意图。两种更新都需要用户或明确业务策略授权，不能仅因为 Effect 可以运行就执行。

当前三方比较把决定交回用户。复杂协作编辑可以引入更细文本模型，但也必须定义合并冲突、撤销和身份语义。对短笔记，少量明确状态比一套看似自动、实际无法解释覆盖来源的同步逻辑更可靠。
