# 第 1 章 从用户任务到可执行的业务规则

一个案件管理应用很容易被写成五组增删改查接口：案件、证据、关联、进度和结论。EchoCase 的实际任务却有次序。调查员先选择案件，逐步调查证据，再根据事实建立联系；材料充分后进入复核，最后提交结论。若允许任意更新数据库字段，用户就可能在尚未调查证据时引用正文，或在结案后继续改写依据。功能清单没有表达这些限制，业务规则必须补上。

## 1.1 案件定义与个人调查不是同一对象

“雾港档案”是固定案件定义，包含题名、嫌疑人和六条证据。它类似一份可重复使用的教学材料。Investigation 则是某位用户针对该案件开启的一次调查，有自己的 Guid、状态、笔记、证据发现与关联。两个用户选择同一案件，不能因此共享已调查标记或结论。

这个区分直接影响数据模型和接口。案件列表提供材料目录，调查列表提供当前用户的档案。客户端不能把案件编号当成调查实例编号，更不能把本地选中案件等同于服务器上的持久进度。创建调查需要可信 owner；读取已有调查需要同时匹配 owner 和调查 Id。身份隔离不是界面筛选的一项便利，而是每次读取和写入都要成立的前提。

总览中的固定案件入口与个人档案列表分开，正是这两个概念在界面中的投影。卡片标题相同不代表资源相同；真正的资源身份是调查 Guid。一次“重新开始”应建立新调查，而不是偷偷把同一个已提交对象恢复成 Active。

## 1.2 把模块连成任务闭环

{{figure business-loop}}

证据管理在这里不是任意上传附件。证据定义固定，一部分线索有前置条件：调查异常门禁记录后才看得到备用凭证领用册，调查领用册后再解锁调度消息。已解锁只说明可以调查，未调查时仍没有正文。界面显示“锁定”“待调查”“已调查”，对应不同事实，不能压成一个布尔值。

证据关联也不是给图上加一条装饰线。它记录调查员认为两条已调查事实互相印证或存在矛盾。关系两端必须属于本次调查已发现的证据，不能自连，也不能把 A-B 和 B-A 当成两条不同关系。关联修订允许判断改变，却保留原关系身份与端点，以便用户理解“同一判断被修正”而非“旧判断被删除后换了另一个对象”。

进度管理包含持久笔记和 Active、Reviewing、Submitted 状态。进入复核需要至少三条已调查证据和两条关联；复核中暂停编辑，允许返回调查补充材料；提交后封存。结论还要选择合法嫌疑人、提供长度合适的理由，并引用至少三条不同的已调查证据。进度条只是从这些事实计算出的呈现，不是可以随意修改的完成率字段。

## 1.3 需求应包含失败后果

“允许修订关联类型和解释”缺少重要语义：哪个状态允许修订，解释的长度单位是什么，其他窗口改动后怎么办，响应丢失时怎样重试。若等接口和数据库都写完后才补这些问题，客户端往往已经形成错误假设。

{{figure requirements}}

把这项需求写成完整句子，可以是：当前用户在 Active 调查中，针对一条已有关系，基于自己已读到的调查版本，修订类型并给出二十至五百个 Unicode 标量值的解释；成功保留关系 Id 与两端，根版本推进一次；失败不留下部分修订。这里同时出现用户目的、允许条件、结果和失败边界。后面各章将分别解释这些承诺如何落实，而不是让每一层都重复同一份校验清单。

“旧窗口得到错误”仍然不够。旧窗口应该保留用户刚输入的解释，并告诉他档案已经变化；服务器应该返回可区分的 412；数据库应该没有留下失败请求的审计或回执。错误处理因此成为功能的一部分。若失败后解释消失，即使服务器正确拒绝了过期请求，整个产品仍违背了用户的合理预期。

| 用户决定 | 成立的事实 | 被拒绝时应保留的东西 |
|---|---|---|
| 调查证据 | 前置已发现、状态可编辑 | 当前档案及尚未发出的输入 |
| 建立关联 | 两端已调查、关系未重复 | 用户的选择，允许重新核对 |
| 修订关联 | Id 存在、版本一致、解释合法 | 原关系和本地解释草稿 |
| 保存笔记 | 状态可编辑、长度合法 | 未确认的新一代输入 |
| 提交结论 | 复核中、支持与说明完整 | 用户判断，不能默默改成别的结论 |

## 1.4 服务端投影也是需求实现

{{code app-presenter}}

SessionPresenter 没有把数据库实体原样序列化。它计算 Locked 和 Examined，只有已调查证据才映射 Body，并把领域枚举变成协议中的字符串。这个选择使未调查正文不进入普通读取结果。仅在浏览器中隐藏正文没有相同意义，因为用户可以查看网络响应。

投影也有代价。SessionView 包含完整调查所需的证据和关系，所以列表读取目前同样返回较宽的对象图。对一个小型固定案件，这能降低前端组合多个查询的复杂度；若档案数、正文或子项数量增长，就需要重新评估列表摘要。需求边界既决定规则，也决定哪种简化暂时合理。

## 1.5 用反例辨认真实范围

假设用户说“多人协同调查”。不能只把 owner 改为 teamId 就宣布支持协作。谁能邀请成员，已有回执归属于谁，成员被移除后是否还能重放，结论由谁封存，草稿如何提示他人编辑，都需要新的业务决定。现有根版本能够拒绝部分并发写入，却没有自动提供协作权限模型。

同样，固定规则产生的 100 分只评价本案支持证据的覆盖和指定嫌疑人，不是现实推理的置信度。教材中的小案件保留了清晰规则，帮助我们研究软件承诺；不能把题材的真实性与技术机制的真实性混为一谈。

需求分析在这里的成果不是更多文档页，而是一组能穿过代码、数据库和界面的判断。当后续设计让某项保证变得昂贵，应回到这些句子讨论取舍。这样，架构选择才有可以检验的理由。

## 1.6 以一段调查故事检查概念

调查员先打开异常门禁记录。此时它可见，但尚未调查，因此只有摘要。完成调查后，正文成为个人档案的一部分，领用册被解锁；领用册仍未调查，不能立即引用它的正文来建立关系。这个小过程要求三个概念分别成立：前置发现决定可见性，本次发现决定正文与可关联资格，调查状态决定能否继续修改。

如果另一窗口刚把调查送入复核，本窗口即使还显示“调查此证据”按钮，服务器仍应拒绝旧决定。需求不能写成“点击按钮后显示正文”，因为那没有说明状态变化之间的竞争。更准确的说法是：当操作提交时仍满足前提，成功发现证据并推进调查版本，随后读模型提供正文；否则保留现有事实并解释拒绝。

到结论阶段，三条支持证据也必须是不同且已调查的项目。这个条件没有要求图中所有关系组成一棵树，也没有验证自然语言推理是否逻辑完备。若把“形成完整证据链”的产品表达当成已经实现的图连通性算法，就会高估现有规则。需求语言中的形象表达，应继续落到明确计算条件。

## 1.7 可用性承诺同样需要边界

“不会丢输入”必须说明发生在哪里。当前工作台在切换页签时保留笔记，在晚到保存和脏刷新时保护文本；关闭页面、返回总览或切换调查则没有持久草稿恢复。若不说明生命周期，用户可能把有限保护理解成浏览器重启后仍可恢复。

“可以重试”也应指明重试对象。网络结果未知时，重试的是已冻结的原操作，不能把当前输入框中新补充的内容自动塞进旧键。当前文本可以继续编辑，但它属于下一项待决定意图。需求因此要分开讨论工作连续性和副作用连续性：前者允许继续写，后者要求先确认原操作。

这些边界并不减损功能价值。它们使文案、按钮状态、接口和恢复动作保持一致，避免界面作出后端从未承诺的保证。
